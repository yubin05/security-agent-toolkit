## 5교시 · 규칙 읽기 · 로그

### 문제 5-1 · 5교시 규칙표로 요청 세 개를 손으로 판정하기

- (가) 세 요청마다 처음 맞은 규칙 번호와 허용 / 차단을 적어 주세요.
  - 쓸 내용: 「A 규칙 ○ · 허용 또는 차단」처럼 세 줄
  - 답:
    - A 규칙 3 허용
    - B 규칙 5 차단
    - C 규칙 5 차단
- (나-1) 🔍 A 와 B 는 같은 부산 지점이 같은 포트로 가는데 결과가 다릅니다. 무엇이 달라서일까요?
  - 쓸 내용: ① 두 요청에서 달라진 값 하나 ② 그 값 때문에 각각 몇 번 규칙에 맞았는지
  - 답: 두 요청에서 달라진 값은 목적지이다. A는 부산 지점에서 업무 포털의 443번으로 가므로 규칙 3에 처음 맞아 허용된다. B는 부산 지점에서 웹메일의 443번으로 가는데, 이를 허용하는 규칙은 없어 규칙 1~4를 지나 규칙 5에서 차단된다. 규칙 2는 직원이 웹메일로 가는 경우이므로 부산 지점의 요청에는 맞지 않는다. 따라서 출발지와 포트가 같아도 목적지가 다르면 적용되는 규칙과 결과가 달라진다.
- (나-2) 🔍 5번 줄을 맨 위(1번 자리)로 올리면 A ~ C 는 각각 어떻게 될까요? 그래서 `any` 규칙은 어디에 둬야 할까요?
  - 쓸 내용: ① A ~ C 의 새 결과 ② `any` 규칙을 둘 위치와 이유
  - 답: 기존 5번인 any → any · any · 차단 규칙을 맨 위로 올리면 A·B·C 모두 새 규칙 1번에서 차단된다. 어떤 요청이든 이 규칙에 처음 일치하고 판정이 끝나므로, 아래의 허용 규칙은 적용되지 않는다. 따라서 이 문제의 모든 요청을 차단하는 규칙은 필요한 허용 규칙 뒤인 맨 아래에 둬야 한다. any가 일부 조건에 들어간 모든 규칙을 무조건 맨 아래에 둔다는 뜻은 아니며, 규칙이 일치하는 범위와 순서를 함께 확인해야 한다.

### 문제 5-2 · 허용된 연결과 막힌 연결을 Wireshark 로 재 보기

- (가-1) 80번 연결의 `[SYN]` 과 `[SYN, ACK]` 두 줄의 `Time` 값, 그리고 두 값의 차이(RTT)를 ms 로 적어 주세요.
  - 쓸 내용: `[SYN]` 줄의 `Time`, `[SYN, ACK]` 줄의 `Time`, 두 값의 차이를 ms 로 계산한 값
  - 답: SYN의 Time은 6.29초, SYN/ACK의 Time은 6.32초이다. 기록한 값으로 계산하면 RTT는 6.32 - 6.29 = 0.03초이며, ms로 바꾸면 약 30ms이다. 처음에는 0.03만 적었지만 초와 ms를 구분해야 한다. 이 계산은 기존에 적은 시간값을 기준으로 하며 패킷 원본을 새로 확인한 값은 아니다.
- (가-2) 81번 연결에서 SYN 이 몇 번 나갔는지, 줄마다의 `Time` 값, 상대에게서 온 것(SYN/ACK · RST · 없음), `curl` 의 마지막 문구를 적어 주세요.
  - 쓸 내용: ① SYN 횟수 ② 줄마다의 `Time` 값 ③ 상대에게서 온 것 ④ `curl` 마지막 문구 한 줄
  - 답: 기록한 SYN은 총 4번으로, 최초 전송 1번과 재전송 3번이다. 각 Time은 37.92초, 38.92초, 40.92초, 44.93초이며 상대에게서 온 SYN/ACK나 RST는 없다고 기록했다. curl의 마지막 문구는 기존 기록 그대로 `curl: (28) Connection timed out after 15007 millisecond`이다. 시간값과 문구는 작성 당시 기록을 보존했으며 이번 보완에서 명령을 다시 실행하거나 패킷 원본과 대조하지는 않았다.
- (나-1) 🔍 81번 연결은 3-way handshake 의 어디에서 멈췄나요? 5.2 의 두 방식 가운데 어느 쪽이고, 그렇게 판단한 근거 화면은 무엇인가요?
  - 쓸 내용: ① 멈춘 단계(SYN · SYN/ACK · ACK 가운데) ② 드롭 / 거부 가운데 하나와 근거 화면
  - 답: SYN을 보낸 뒤 SYN/ACK를 받지 못해 handshake의 첫 단계에서 더 진행하지 못했다. 기록한 Wireshark 관찰은 SYN 전송과 재전송만 있고 상대의 SYN/ACK·RST가 없다는 것이며, curl도 응답을 기다리다 시간 초과로 끝났다. 따라서 수업의 드롭과 거부 중에서는 응답 없이 버리는 드롭에 해당하는 모습으로 판단한다. 다만 응답이 없다는 사실만으로 어느 방화벽이 버렸는지 확정할 수는 없으며, 실제 원인과 위치를 찾으려면 방화벽 로그·서버 상태·통신 경로를 함께 확인해야 한다.
- (나-2) 81번 SYN 줄의 `Time` 값으로 SYN 사이의 간격을 구해 적어 주세요. 간격은 일정했나요, 늘어났나요?
  - 쓸 내용: ① (가-2) 의 `Time` 값으로 구한 줄 사이 간격 두 가지(앞부분 · 뒷부분, 예: 1.0초, 2.0초) ② 간격이 일정했는지, 늘어났는지
  - 답: 기록한 Time 값으로 계산한 간격은 38.92 - 37.92 = 1.00초, 40.92 - 38.92 = 2.00초, 44.93 - 40.92 = 4.01초이다. 간격은 일정하지 않고 약 1초, 2초, 4초로 늘어났다. 응답이 없을 때 계속 같은 속도로 요청을 보내는 대신 재전송 대기 시간을 늘리는 모습이다. 계산값의 정밀도는 기존에 기록한 소수 둘째 자리 시간값을 따른다.
- (다) 아래 방화벽 로그의 14:05 네 줄을 `10.8.0.21` PC 쪽에서 패킷으로 보면 어떤 모습일까요? 무엇을 하려던 기록으로 보이는지, 다음에 어떤 기록을 확인하면 좋을지도 적어 주세요.
  - 쓸 내용: ① 패킷으로 보이는 모습(무엇을 보내고 무엇이 안 왔는지) ② 목적지 · 포트 · 간격으로 본 행동 ③ 다음에 확인할 기록
  - 답: 수업의 드롭 상황에서 PC 쪽 Wireshark에는 아래처럼 각 목적지로 보내는 SYN이 보이고, 그에 대한 SYN/ACK나 RST는 돌아오지 않는다. 방화벽 로그의 차단·규칙 5라는 문구가 PC의 패킷 목록에 표시되는 것은 아니다.

    ```text
    방향: 출발지 PC → 목적지 서버       TCP 플래그
    10.8.0.21:51710 → 10.10.20.9:22     [SYN]
    10.8.0.21:51711 → 10.10.20.9:443    [SYN]
    10.8.0.21:51712 → 10.10.30.7:3306   [SYN]
    10.8.0.21:51713 → 10.10.30.8:5432   [SYN]

    각 연결: SYN 전송 → 응답 없음 → 일정 시간 뒤 SYN 재전송 → 응답 없음
    ```

    위 그림은 방화벽 로그를 바탕으로 예상한 PC 측 패킷 모습이며 실제 캡처를 옮긴 것은 아니다. 응답 없음은 패킷 한 줄이 생긴다는 뜻이 아니라, 대응하는 수신 패킷이 관찰되지 않는다는 뜻이다. 재전송 시각과 횟수는 이 방화벽 로그 네 줄만으로 알 수 없다.

    서로 다른 서버의 SSH(22), HTTPS(443), MySQL(3306), PostgreSQL(5432)에 1초 간격으로 연결을 시도하므로, 열린 서비스를 찾는 내부 스캔이 의심된다. 네 줄은 서로 다른 연결 시도이며 같은 연결의 재전송 네 번이 아니다. 다음에는 해당 시각의 VPN 게이트웨이 접속 로그에서 10.8.0.21을 배정받은 계정과 원래 접속 공인 IP를 확인한다. 승인된 점검일 수도 있으므로 점검 일정과 해당 PC의 실행 프로그램, 이후 허용·성공한 접속 기록도 대조해 실제 공격인지 판단해야 한다.

- (라) (선택) 사용자가 「회사 서버에 접속이 안 된다」고 합니다. 패킷만 보고 방화벽 문제인지 서버 문제인지 어떻게 나눌 수 있을까요?
  - 쓸 내용: 응답이 아예 없을 때 · RST 가 올 때 · SYN/ACK 가 올 때 각각 무엇을 의심하고 먼저 어디를 볼지. 선택 문항이라 안 쓰면 「선택 안 함」이라고 적습니다
  - 답: SYN을 보냈는데 응답이 전혀 없으면 방화벽 드롭뿐 아니라 패킷 손실, 서버 중단, 경로 문제도 가능하므로 방화벽 로그와 서버·경로 상태를 대조한다. RST가 오면 서버에서 해당 포트를 받는 프로그램이 없거나 방화벽이 접속을 거부한 것일 수 있어 서비스 실행 상태와 거부 규칙을 함께 확인한다. SYN/ACK가 오면 서버 측 응답은 돌아왔으므로 마지막 ACK로 handshake가 완료됐는지 확인하고, 완료됐다면 응용 프로그램의 요청·응답과 서버 로그를 살펴본다. 처음에는 방화벽이 차단하지 않았으면 서버 문제라고 생각했지만, 패킷만으로 원인을 이분법적으로 확정할 수는 없다.

### 이 교시에 새로 안 것

- 이 교시에서 새로 알게 된 것 하나를 적어 주세요. (「이 교시에 새로 안 것」 칸)
  - 쓸 내용: 새로 안 것 하나와, 그게 왜 기억에 남는지
  - 답: 같은 통신도 방화벽 로그와 PC의 패킷 화면에서는 다르게 보인다는 것을 새로 알게 됐다. 처음에는 방화벽 로그를 그대로 옮기면 PC에서 본 모습이 되는 줄 알았지만, 수업의 드롭 상황에서 PC에는 SYN 전송과 재전송이 보이고 상대의 SYN/ACK나 RST는 돌아오지 않는다. 차단·규칙 5라는 판정은 방화벽 로그에 남는 정보이므로 PC 패킷과 대조해야 한다는 점이 기억에 남는다. 또한 SYN과 SYN/ACK의 Time 차이 0.03은 초 단위여서 약 30ms로 바꿔 적어야 하며, 응답이 없다는 사실만으로 어느 방화벽에서 막혔는지나 서버가 꺼졌는지를 단정할 수 없다는 것도 알게 됐다.

## 6교시 · 허용 목록 · 규칙 순서

### 문제 6-1 · 학원 방화벽은 허용 목록일까 차단 목록일까

- (가) 포트 443 · 445 · 3389 마다 「열림 · 드롭 · 거부」 판정과 근거(`curl` 문구 · Wireshark 화면)를 한 줄씩 적어 주세요.
  - 쓸 내용: 「443: 열림 — Port test successful!」처럼 포트마다 한 줄, 판정과 근거
  - 답:
    - 443: 열림으로 판단 — 이번에 Wireshark에서 SYN 전송과 SYN/ACK 수신을 확인했다. 서버 측 TCP 응답이 돌아온 근거이며, 연결 수립 완료까지 확인하려면 마지막 ACK도 확인해야 한다. HTTP 시험 결과만으로 HTTPS 서비스나 로그인 성공까지 확인한 것은 아니다.
    - 445: 드롭 추정 — 이번 관찰에서는 SYN이 계속 재전송됐다. 응답도 보이는 2번 필터에서 같은 연결의 SYN/ACK·RST가 없는지 확인하면 수업의 드롭 패턴에 해당한다. 이번 확인에서 curl의 최종 문구와 재전송 횟수는 별도로 기록하지 않았다.
    - 3389: 드롭 추정 — 이번 관찰에서는 445와 마찬가지로 SYN 재전송이 반복됐다. 따라서 기존의 성공 문구만 근거로 적었던 열림 판정을 수정한다. 응답도 보이는 2번 필터에서 같은 연결의 SYN/ACK·RST 유무를 확인해야 하며, 기존 성공 문구와 이번 캡처가 같은 실행·목적지 IP·포트를 가리키는지도 대조할 필요가 있다.

- (나) 🔍 이 결과로 보면 학원 방화벽은 허용 목록과 차단 목록 가운데 어느 쪽에 가까운가요? 근거가 된 포트를 들어 적어 주세요.
  - 쓸 내용: ① 허용 목록 / 차단 목록 / 알 수 없음 가운데 하나 ② 근거가 된 포트와 그 결과 ③ 안내 6.1 표의 어느 줄과 맞는지
  - 답: 이번 패킷 관찰은 443에서 SYN/ACK가 돌아오고 445·3389에서는 SYN 재전송이 반복되는 모습이다. 후자의 두 포트에 응답이 없는 것이 확인된다면, 수업의 6.1 비교표에서 필요한 포트만 열고 나머지는 막는 허용 목록 쪽 설명에 가깝다고 추정한다. 기존에는 3389도 열림으로 적어 차단 목록에 가깝다고 썼지만, 새 관찰에 맞춰 판단을 수정했다. 다만 세 포트와 목적지 하나의 결과만으로 실제 기본 정책을 확정할 수는 없고, 445·3389는 시작 SYN만 보이는 필터가 아닌 전체 응답이 보이는 필터에서 확인해야 한다.

- (다-1) 포트 세 개만 보고 내린 판단에는 어떤 한계가 있을까요? 더 확실하게 알려면 무엇을 더 해야 할까요?
  - 쓸 내용: ① 한계 한 가지 ② 더 해야 할 시험 한 가지
  - 답: 시험한 포트가 443·445·3389 세 개이고 목적지도 portquiz.net 하나뿐이라, 다른 포트나 목적지에 적용되는 정책과 방화벽의 기본 동작까지 알 수는 없다. 허가된 범위에서 다른 포트와 다른 목적지에도 같은 시험을 해 결과를 비교해야 한다. 가능하면 실제 방화벽 규칙과 로그도 대조해 허용 목록인지 차단 목록인지 확인한다.
- (다-2) 6번 필터(`tcp.flags.syn == 1 && tcp.flags.ack == 0`)로 바꾸니 2번 필터 화면에서 어떤 패킷이 사라졌나요? 한 PC 가 여러 포트로 연결을 시작한 것을 찾을 때 이 필터를 쓰는 이유는 무엇일까요?
  - 쓸 내용: ① 사라진 패킷의 종류 ② 시작 SYN 만 모아 볼 때 알 수 있는 것
  - 답: tcp.flags.syn == 1 && tcp.flags.ack == 0은 SYN 비트가 1이고 ACK 비트가 0인 패킷만 남기므로, SYN/ACK와 일반 ACK·일반적인 데이터 패킷 및 SYN이 없는 RST 등은 화면에서 사라진다. 연결 시작 SYN을 모으면 한 PC가 어떤 목적지·포트에 연결을 시도했는지 파악하기 쉽다. 다만 최초 SYN과 SYN 재전송이 모두 포함되므로 패킷 수가 곧 서로 다른 연결의 수는 아니다. 처음에는 이 화면에 SYN만 반복해서 보이면 드롭이라고 생각했지만, 필터가 응답을 숨긴 결과일 수도 있으므로 그렇게 판정하면 안 된다. 열림·드롭·거부를 판단하려면 응답도 보이는 2번 필터로 돌아가 SYN/ACK·RST 유무와 curl 결과를 함께 확인해야 한다.

### 문제 6-2 · 허용했는데 왜 막힐까 — 규칙 순서 고치기

- (가-1) 처음 규칙표로 판정한 세 요청의 처음 맞은 규칙 번호와 허용 · 차단을 적어 주세요.
  - 쓸 내용: 「A 규칙 ○ · 허용 또는 차단」처럼 세 줄
  - 답: A 규칙 1 · 차단 / B 규칙 1 · 차단 / C 규칙 1 · 차단. 세 요청 모두 출발지가 VPN 직원 범위에 속하고 목적지가 본사 전체 범위에 포함되므로, 포트를 any로 차단하는 첫 규칙에서 멈춘다.
- (가-2) 2번과 3번을 위로 올린 규칙표로 판정한 세 요청의 처음 맞은 규칙 번호(올린 뒤의 번호)와 허용 · 차단을 적어 주세요.
  - 쓸 내용: 「A 규칙 ○ · 허용 또는 차단」처럼 세 줄
  - 답: A 규칙 1 · 허용 / B 규칙 2 · 허용 / C 규칙 3 · 차단. 순서를 바꾼 뒤에는 업무 포털 허용이 1번, 웹메일 허용이 2번, 본사 전체 차단이 3번, 모두 차단이 4번이다. 처음에는 옮기기 전 번호로 적었지만, 이 문항은 재배치한 뒤 위에서부터 다시 센 번호를 적어야 한다.
- (나) 🔍 처음 규칙표에서 업무 포털 허용 규칙(2번)이 있는데도 왜 막혔을까요?
  - 쓸 내용: ① 처음 규칙표 1번의 목적지 범위와 포트 ② 업무 포털 주소가 그 범위에 들어 있는지 ③ 그래서 2번까지 가지 못한 이유
  - 답: 처음 규칙표의 1번은 VPN 직원 10.8.0.0/24에서 본사 전체 10.10.0.0/16으로 가는 모든 포트(any)를 차단한다. 업무 포털 10.10.20.5는 본사 범위 10.10.0.0~10.10.255.255 안에 있고, 포트 443도 any에 포함된다. 요청 A의 출발지 10.8.0.21도 VPN 직원 범위 안에 있으므로 출발지·목적지·포트가 모두 1번에 맞는다. 첫 번째로 일치한 규칙에서 판정을 끝내기 때문에 아래의 업무 포털 허용 규칙 2번까지 내려가지 못한다.
- (다) 반대로 「부산 지점(`192.168.20.0/24`) → 본사 전체(`10.10.0.0/16`) · `any` · 허용」 규칙이 「부산 지점 → 고객 DB(`10.10.30.7/32`) · `3306` · 차단」 규칙보다 위에 있으면, 부산 지점에서 고객 DB 로 가는 요청은 어떻게 될까요? 어떤 사고가 날까요?
  - 쓸 내용: ① 그 요청이 먼저 맞는 규칙 ② 그래서 생기는 사고
  - 답: 부산 지점에서 고객 DB 10.10.30.7의 3306번으로 가는 요청은 위에 있는 부산 지점 192.168.20.0/24 → 본사 전체 10.10.0.0/16 · any · 허용 규칙에 먼저 맞는다. 고객 DB 주소가 본사 전체 범위 안에 있고 포트 3306도 any에 포함되므로, 아래의 고객 DB 차단 규칙은 적용되지 않는다. 따라서 부산 지점 범위의 PC가 고객 DB로 통신을 시도할 수 있게 되어 불필요한 접근과 정보 유출 위험이 생긴다. 다만 방화벽 허용만으로 DB 인증이나 데이터 탈취까지 성공했다고 단정할 수는 없다. DB 차단을 우선 적용하려는 정책이라면 해당 차단 규칙을 넓은 허용 규칙보다 위에 둬야 한다.

### 이 교시에 새로 안 것

- 이 교시에서 새로 알게 된 것 하나를 적어 주세요. (「이 교시에 새로 안 것」 칸)
  - 쓸 내용: 새로 안 것 하나와, 그게 왜 기억에 남는지
  - 답: 방화벽은 허용 규칙이 있는지만 보는 것이 아니라, 위에서부터 처음 일치한 규칙으로 결정한다는 점을 새로 알게 됐다. 업무 포털 허용 규칙이 있어도 그 위의 본사 전체 차단 규칙에 먼저 맞으면 접속이 막히고, 반대로 넓은 허용 규칙이 먼저 있으면 아래의 DB 차단 규칙은 적용되지 않는다. 규칙 내용이 같아도 순서를 바꾸면 결과가 달라지고, 옮긴 뒤에는 번호도 다시 세어야 한다는 점이 기억에 남는다. 또한 443에서 SYN/ACK가 보이고 445·3389에서 SYN 재전송이 보였던 관찰을 통해, 시작 SYN만 남기는 필터로는 응답 유무를 판단할 수 없으며 전체 응답이 보이는 필터에서 확인해야 한다는 것도 알게 됐다.

### 문제 7-1 · 요구사항을 읽고 규칙표 직접 쓰기

- (가) 처음 실행했을 때의 점수와, `점수: 8 / 8` 이 나올 때까지 몇 번 고쳤는지 적어 주세요.
  - 쓸 내용: 처음 점수 하나와 고친 횟수 하나
  - 답: 처음 실행은 문법 오류로 종료되어 점수가 나오지 않았고, 오류를 수정한 뒤 기록한 점수는 8 / 8이다. 현재 코드도 검수 시 직접 실행해 8 / 8을 확인했다. 정확히 몇 번 수정했는지는 당시 기록이 없어 확인하지 못했으며, 제출 전 실제 수정 횟수를 확인해 추가해야 한다.
- (나-1) 처음에 틀렸던 시험 하나를 골라, 어느 규칙이 왜 틀렸고 어떻게 고쳤는지 적어 주세요. 한 번에 8 / 8 이었다면, 위에서 다섯째 시험(지점 → 관리 서버 `443`)이 왜 차단되어야 하는지 적어 주세요.
  - 쓸 내용: ① 틀렸던 시험 번호 ② 원인이 된 규칙과 이유 ③ 고친 내용 — 한 번에 맞았으면 시험 5번이 차단되어야 하는 이유(요구사항 ② 의 「만」)
  - 답: 기존 기록에는 문법 오류 수정 뒤 8 / 8이라고 적혀 있으므로, 틀렸던 시험을 임의로 만들지 않고 시험 5번의 차단 이유를 설명한다. 요구사항 ②는 부산 지점에 업무 포털과 웹메일의 HTTPS(443)만 허용한다. 시험 5번은 부산 지점 192.168.20.15에서 관리 서버 10.10.20.9의 443번으로 가는 요청이어서, 포트가 같아도 허용 대상 서버가 아니다. 현재 규칙 3·4는 목적지를 업무 포털 10.10.20.5/32와 웹메일 10.10.20.6/32로 한정하므로 이 요청에 맞지 않고, 규칙 7의 모두 차단에 처음 맞아 차단된다.
- (나-2) 🔍 부산 지점 규칙의 목적지를 서버 하나(`/32`)가 아니라 같은 서버 범위 전체 `10.10.20.0/24` 로 적으면 8개 가운데 어느 시험이 틀릴까요? 요구사항 ② 와 비교해 이유를 적어 주세요.
  - 쓸 내용: ① 틀릴 시험 번호 ② `10.10.20.0/24` 에 들어 있는 서버들 ③ 요구사항 ② 보다 넓게 열리는 이유
  - 답: 시험 5번인 부산 지점 → 관리 서버 10.10.20.9 · 443이 허용으로 판정되어 틀린다. 10.10.20.0/24의 범위는 10.10.20.0~10.10.20.255이며, 업무 포털 10.10.20.5와 웹메일 10.10.20.6뿐 아니라 관리 서버 10.10.20.9도 포함한다. 부산 지점 허용 규칙의 목적지를 이 범위로 넓히면 관리 서버의 443번도 먼저 허용되어, 업무 포털과 웹메일만 쓴다는 요구사항 ②보다 넓게 열린다. 따라서 현재 규칙처럼 서버 한 대를 가리키는 /32로 제한해야 한다.
- (다) 내 규칙표에서 고객 DB(`10.10.30.7`)로 가는 통신을 허용하는 규칙은 몇 줄이고, 누구에게 열려 있나요? 이것이 「DB 서버가 불필요하게 노출되지 않았는가」 기준을 어떻게 지키는지 적어 주세요.
  - 쓸 내용: ① DB 로 가는 허용 규칙 수와 그 출발지 ② 나머지(VPN 직원 · 지점 · 인터넷)가 어느 규칙에 맞는지 ③ 그래서 DB 가 노출되지 않는 이유
  - 답: 고객 DB로 가는 허용 규칙은 규칙 5번 한 줄이며, 출발지는 업무 포털 서버 10.10.20.5/32 한 대이고 목적지는 고객 DB 10.10.30.7/32의 3306번이다. VPN 직원·부산 지점·인터넷에서 고객 DB로 직접 가는 요청은 허용 규칙에 맞지 않아 규칙 7에서 차단된다. DB와 통신할 수 있는 출발지와 포트를 필요한 범위로 제한해 불필요한 직접 접근을 막는 것이다. 처음에는 직원의 통신이 업무 포털을 거쳐 그대로 DB로 전달되는 것처럼 썼지만, 직원·지점 PC → 업무 포털 연결과 업무 포털 서버 → DB 연결은 별도이다. 이 방화벽 규칙만으로 포털의 업무 기능이나 DB 인증·권한 설정까지 보장되는 것은 아니다.

### 문제 7-2 · 요구사항이 바뀌었다 — 규칙 한 줄을 어디에 넣을까

- (가) 새로 넣은 규칙 한 줄과, 규칙표에서 몇 번째에 넣었는지 적어 주세요.
  - 쓸 내용: 새 규칙 한 줄을 그대로, 그리고 몇 번째 줄인지
  - 답: 새 규칙은 `(7, "10.8.0.50/32", "10.10.20.9/32", 22, "허용"),`이며, 규칙표의 7번째인 모두 차단 규칙 바로 위에 넣었다. 기존 모두 차단 규칙은 8번으로 바꿨다. 현재 코드의 실행 결과는 점수: 10 / 10으로 검수에서 확인했다.
- (나-1) 🔍 출발지를 `10.8.0.50/32` 가 아니라 `10.8.0.0/24` 로 적으면 10개 가운데 어느 시험이 틀릴까요? 실제로는 어떤 일이 생길까요?
  - 쓸 내용: ① 틀릴 시험 번호 ② `10.8.0.0/24` 가 누구까지 포함하는지 ③ 실제로 생길 수 있는 일
  - 답: 시험 10번인 다른 VPN 직원 10.8.0.21 → 관리 서버 10.10.20.9 · 22가 차단되어야 하는데 허용으로 판정되어 틀린다. 출발지 범위 10.8.0.0/24는 10.8.0.0~10.8.0.255이므로 관리자 10.8.0.50뿐 아니라 다른 VPN 직원 주소도 포함한다. 그러면 관리자 한 명에게만 열어야 하는 관리 서버 SSH가 VPN 직원 전체에게 열려, 다른 직원이나 탈취된 직원 계정으로도 SSH 접속을 시도할 수 있게 된다. 따라서 새 규칙의 출발지는 관리자 주소 하나인 10.8.0.50/32로 제한해야 한다.
- (나-2) 새 규칙을 「모두 차단」 줄 **아래**에 넣으면 어느 시험이 틀릴까요? 왜 그럴까요?
  - 쓸 내용: ① 틀릴 시험 번호 ② 그 요청이 먼저 맞는 규칙 번호와, 그래서 새 규칙까지 못 가는 이유
  - 답: 시험 9번인 재택 관리자 10.8.0.50 → 관리 서버 10.10.20.9 · 22가 허용되어야 하는데 차단되어 틀린다. 현재 규칙표는 관리자 허용 7번 다음에 모두 차단 8번이 있다. 이 두 줄의 위치를 바꾸고 위에서부터 번호를 다시 매기면 모두 차단이 7번, 관리자 허용이 8번이 된다. 요청은 모두 차단 7번에 먼저 일치해 판정이 끝나므로 아래의 관리자 허용 8번까지 내려가지 못한다. 만약 기존 번호를 유지하고 위치만 바꿨다면 먼저 맞는 규칙의 표시는 8번이지만, 차단이 먼저 적용되는 이유는 같다.

  - 쓸 내용: ① 방화벽이 보는 것과 보지 않는 것 ② 비밀번호를 탈취한 공격자가 받는 주소 ③ 오전 4-2 에서 본 VPN 의 한계와 이어서
  - 답: 이 실습의 방화벽은 출발지 주소·목적지 주소·목적지 포트를 규칙과 비교하고, 일치한 규칙의 동작(action)을 적용한다. action은 관찰하는 입력값이 아니라 허용·차단을 정하는 결과이며, 방화벽은 실제 접속자가 관리자 본인인지까지 확인하지 않는다. 수업처럼 관리자 계정에 VPN 주소 10.8.0.50을 배정하는 설정이라면, 비밀번호를 훔친 공격자가 그 계정으로 VPN 인증을 통과했을 때 같은 주소를 받아 관리 서버 SSH 통신도 허용될 수 있다. 4-2에서 VPN 로그인 뒤 업무와 무관한 서버까지 허용됐던 것처럼, 인증된 주소라는 사실만으로 실제 사용자를 신뢰하는 데 한계가 있다. 따라서 MFA와 접속 기기 확인 등 추가 통제가 필요하다. 다만 비밀번호 탈취가 반드시 VPN 인증 성공을 뜻하지 않으며, VPN과 방화벽을 통과했더라도 별도의 SSH 인증·권한 확인까지 성공해야 하므로 서버 장악이 불가피하다고 단정해서는 안 된다.

### 2. 설계 원칙 — 강의계획서의 평가 기준 세 가지

- 허용 목록(화이트리스트 · 최소 권한)을 어떻게 적용했나요?
  - 쓸 내용: ① 맨 아래 줄의 번호와 동작 ② 요구사항의 「만」을 지키려고 `/32` 로 좁힌 규칙 번호 하나와 이유
  - 답: 맨 아래 규칙 8번을 any → any · any · 차단으로 두고, 그 위에는 요구사항에 필요한 통신만 허용했다. 예를 들어 부산 지점 허용 규칙 3·4번은 목적지를 본사 서버 망 전체가 아니라 업무 포털 10.10.20.5/32와 웹메일 10.10.20.6/32로 한정하고 포트도 443으로 제한했다. 재택 관리자 규칙 7번 역시 출발지를 10.8.0.50/32 한 주소로 좁혀 다른 VPN 직원까지 관리 서버 SSH를 사용하지 못하게 했다. 이렇게 허용 목록과 최소 권한을 적용했다.
- 규칙 순서는 어떤 원칙으로 정했나요?
  - 쓸 내용: ① 좁은 규칙과 넓은 규칙의 위치 ② 7-2 에서 새 규칙을 넣은 위치와 이유(6-2 · 7-2 참고)
  - 답: 첫 번째로 일치한 규칙에서 판정이 끝나므로, 이 설계에서는 필요한 좁은 허용 규칙을 먼저 두고 넓은 모두 차단 규칙을 맨 아래에 뒀다. 7-2에서 추가한 재택 관리자 허용 규칙은 7번째, 모두 차단 8번 바로 위에 배치했다. 순서를 반대로 두면 관리자 요청도 모두 차단에 먼저 일치해 허용 규칙이 적용되지 않는다. 좁은 규칙이 언제나 무조건 먼저라는 뜻보다는, 겹치는 규칙 중 어떤 정책을 먼저 적용할지 확인하는 것이 중요하다.

  - 쓸 내용: ① DB 로 가는 허용 규칙 번호와 출발지 ② 그 밖의 출발지가 맞는 규칙
  - 답: 고객 DB로 가는 허용 규칙은 5번 한 줄이며, 출발지는 업무 포털 서버 10.10.20.5/32, 목적지는 고객 DB 10.10.30.7/32, 포트는 3306으로 제한했다. VPN 직원·부산 지점·인터넷 등 다른 출발지의 DB 직접 접근은 규칙 8번에서 차단된다. 사용자 PC → 업무 포털 연결과 업무 포털 서버 → DB 연결은 별개이며, 포털을 거친다는 사실 자체를 보안 이중화라고 표현하는 것은 부정확하다. 핵심은 DB에 직접 접근할 수 있는 출발지를 필요한 서버 한 대로 제한하는 것이고, DB 자체 인증과 권한 통제도 함께 필요하다.

  - 쓸 내용: ① 막지 못하는 상황 하나(예: 계정을 빼앗긴 VPN 직원) ② 방화벽이 그것을 못 막는 이유(방화벽이 보는 것) ③ 더 필요한 확인 하나
  - 답: 공격자가 탈취한 VPN 계정으로 인증을 통과하고 그 계정에 허용된 VPN 주소를 배정받으면, 이 규칙표는 실제 사용자가 본인인지 구별하지 못해 해당 주소에 허용된 통신을 허용할 수 있다. 예를 들어 재택 관리자 계정에 10.8.0.50이 배정되는 설정이면 관리 서버 SSH 통신이 규칙 7번에 맞을 수 있다. 이 실습의 방화벽은 출발지·목적지·포트를 비교하므로, MFA와 접속 기기 확인, 로그인 이후 행동 점검 같은 추가 확인이 필요하다. 다만 비밀번호 탈취가 반드시 VPN 인증 성공을 뜻하지 않으며, 방화벽 통과도 SSH·DB 인증이나 데이터 탈취의 성공을 뜻하지는 않는다.
