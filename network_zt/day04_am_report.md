## 2교시 · VPN 과 터널

### 문제 2-1 · VPN 에 연결한 PC 의 어댑터 읽기

- (가-1) 연결 전 화면과 연결 후 화면에서 어댑터 이름 줄은 각각 몇 개이고, 연결 후에 새로 생긴 어댑터 이름은 무엇인가요?
  - 쓸 내용: 연결 전 개수, 연결 후 개수, 새로 생긴 어댑터 이름 하나. `미디어 연결 끊김` 어댑터도 센다
  - 답: 연결 전 2개 / 연결 후 3개 / 새로 생긴 어댑터: PPP 어댑터 CompanyVPN. 미디어 연결 끊김 상태의 어댑터도 개수에 포함했다.
- (가-2) 연결 후 화면에서 새 어댑터의 IPv4 주소와, 이더넷 어댑터의 IPv4 주소를 적어 주세요.
  - 쓸 내용: 「새 어댑터: … / 이더넷: …」처럼 주소 두 개. `서브넷 마스크` 줄은 적지 않는다
  - 답: 새 어댑터: 10.8.0.21 / 이더넷: 192.168.200.81.
- (나) 🔍 새 어댑터의 IPv4 주소는 이더넷 어댑터의 주소와 같은 범위일까요, 다른 범위일까요? 왜 그럴까요?
  - 쓸 내용: ① 「같다 / 다르다」 하나 ② 이더넷 어댑터의 주소는 어느 망에서 받은 것인지 ③ 새 어댑터의 주소는 누가 어느 범위에서 나눠 주는지(안내 2.1 의 「VPN 주소」 뜻)
  - 답: 다르다. 이더넷 어댑터의 192.168.200.81은 현재 PC가 연결된 집·학원 같은 로컬 망에서 받은 주소이다. 새 VPN 어댑터의 10.8.0.21은 회사 VPN 게이트웨이가 회사에서 정한 VPN 주소 풀에서 배정한 주소이므로 기존 이더넷 주소와 범위가 다르다. 기존 이더넷 어댑터도 그대로 남아 VPN 터널로 감싼 패킷을 실제 인터넷으로 내보내는 데 사용된다.
- (다) 회사 서버의 접속 로그(VPN 접속마다 남는 기록, 4교시에서 읽습니다)에는 VPN 으로 들어온 직원의 출발지가 집 공인 IP 가 아니라 VPN 주소로 남습니다. 관제 담당자가 VPN 주소만 보고는 알 수 없는 것은 무엇일까요?
  - 쓸 내용: ① VPN 주소는 누가 나눠 준 주소인지 ② 그래서 VPN 주소만으로 알 수 없는 것 한두 가지(어디서 · 누가)
  - 답: VPN 주소는 회사 VPN 게이트웨이가 접속한 PC에 배정한 주소이다. 이 주소만으로는 사용자가 실제 어느 공인 IP에서 접속했는지, 어느 계정으로 접속한 사용자인지 확정할 수 없다. 같은 VPN 주소가 나중에 다른 사용자에게 배정될 수도 있기 때문이다. 처음에는 회사 주소인지 확인하는 문제라고 생각했지만, 핵심은 VPN 주소만으로 실제 접속 출처와 사용자를 특정할 수 없다는 점이다. 접속 시각을 기준으로 VPN 게이트웨이 로그의 계정·접속한 공인 IP·배정된 VPN 주소를 함께 대조해야 한다. 계정이 확인되더라도 실제 접속자가 계정 주인인지는 추가 확인이 필요하다.

### 문제 2-2 · 캡슐화된 패킷 — 암호화하면 무엇이 안 보이나

- (가-1) `day04_2-2_tunnel_plain.py` 를 실행했을 때 나온 세 줄을 그대로 옮겨 적어 주세요.
  - 쓸 내용: 터미널 출력 세 줄을 복사해 붙여 넣기
  - 답:
    ```text
    중간 라우터가 보는 도착지: 203.0.113.1
    data 칸: {'src': '10.8.0.21', 'dst': '10.10.20.5', 'data': 'GET /portal'}
    안쪽 도착지: 10.10.20.5
    ```
- (가-2) `day04_2-2_tunnel_encrypted.py` 를 실행했을 때 나온 두 줄과, 맨 마지막 줄의 에러 이름을 적어 주세요.
  - 쓸 내용: 출력 두 줄과, 맨 마지막 줄의 `:` 앞 에러 이름 하나
  - 답:
    ```text
    중간 라우터가 보는 도착지: 203.0.113.1
    data 칸: k8Zq0x7RmP2aWv9L
    Traceback (most recent call last):
      File "G:\My Drive\security-agent-toolkit\network_zt\day04_2-2_tunnel_encrypted.py", line 5, in <module>
        print("안쪽 도착지:", outer["data"]["dst"])                               # data 칸에서 dst 를 한 번 더 꺼내 출력하려고 한다
                              ~~~~~~~~~~~~~^^^^^^^
    TypeError: string indices must be integers, not 'str'
    ```
    에러 이름: `TypeError`. 앞의 두 출력 줄은 코드와 수업 자료를 대조해 보완했으며, 아래 Traceback은 기존 기록을 보존했다.
- (나-1) 두 파일 모두 중간 라우터가 보는 도착지는 `203.0.113.1` 입니다. 왜 업무 포털 서버 주소 `10.10.20.5` 가 아닐까요?
  - 쓸 내용: ① 사내(사설) 주소 `10.10.20.5` 가 공용 인터넷 라우터의 라우팅 표에 있는지(10/13 사설 주소) ② 그래서 바깥 헤더의 도착지에 무엇을 적는지
  - 답: 업무 포털의 10.10.20.5는 사설 주소이므로 공용 인터넷에서 회사의 해당 서버까지 직접 라우팅되는 주소가 아니다. 따라서 바깥 헤더의 도착지에는 인터넷을 통해 찾아갈 회사 VPN 게이트웨이 주소 203.0.113.1을 적는다. 중간 라우터들은 이 바깥 도착지를 기준으로 전달하고, VPN 게이트웨이가 바깥 헤더를 벗기고 복호화한 뒤 안쪽 패킷을 업무 포털로 전달한다. 여기서 203.0.113.1은 수업에서 공인 주소 역할로 사용한 문서·예시용 주소이다.
- (나-2) 🔍 두 번째 파일은 왜 마지막 줄에서 에러가 나며 멈췄을까요? 중간에서 패킷을 가로채 보는 사람(도청자)에게 이것은 무엇을 뜻할까요?
  - 쓸 내용: ① 두 번째 파일의 `data` 칸에 든 것이 딕셔너리인지 글자인지 ② 그래서 `["dst"]` 로 꺼낼 수 없는 이유 ③ 도청자가 볼 수 있는 것과 볼 수 없는 것
  - 답: 두 번째 파일의 data 칸은 딕셔너리가 아니라 문자열이므로, 문자열 위치를 나타내는 정수 대신 "dst"라는 키로 접근하면 TypeError가 발생한다. 처음에는 딕셔너리가 아니면 데이터도 아니라고 생각했지만, 문자열도 데이터이며 단지 값을 꺼내는 방식이 다르다. 이 실습의 문자열은 암호문을 나타내는 예시이고, 코드가 실제 암호화를 수행한 것은 아니다. 실제로 암호화된 터널을 중간에서 관찰하는 도청자는 바깥 출발지인 집 공인 IP와 도착지인 회사 VPN 게이트웨이 주소 및 암호문을 볼 수 있지만, 복호화 키 없이는 안쪽 사내 주소와 요청 내용을 읽을 수 없다. 바깥 헤더의 목적지는 다음 라우터 주소가 아니라 터널의 끝인 VPN 게이트웨이 주소이다.
- (다) 첫 파일처럼 터널은 있지만 암호화하지 않은 VPN 으로 카페 와이파이에서 접속하면, 같은 와이파이의 공격자는 무엇을 알 수 있을까요?
  - 쓸 내용: ① 첫 파일의 `data` 칸이 그대로 보이면 알 수 있는 값 두 가지 이상 ② 터널과 암호화가 같은 것인지
  - 답: 문제처럼 공격자가 암호화되지 않은 안쪽 data를 볼 수 있다면, 출발지 VPN 주소 10.8.0.21, 사내 서버 주소 10.10.20.5, 요청 내용 GET /portal을 알 수 있다. 터널링은 원래 패킷을 다른 패킷 안에 넣어 감싸는 것이고, 암호화는 키 없이 내용을 읽기 어렵게 만드는 것이므로 서로 다르다. 따라서 터널이 있다는 것만으로 안쪽 내용이 숨겨지는 것은 아니며, 회사 VPN에서 터널과 암호화를 함께 사용하는지 확인해야 한다.

### 이 교시에 새로 안 것

- 이 교시에서 새로 알게 된 것 하나를 적어 주세요. (「이 교시에 새로 안 것」 칸)
  - 쓸 내용: 새로 안 것 하나와, 그게 왜 기억에 남는지
  - 답: 터널링과 암호화는 서로 다른 기능이라는 것을 새로 알게 됐다. 처음에는 패킷을 한 번 더 감싸면 내용도 숨겨질 것 같았지만, 첫 번째 코드에서는 터널 안의 사내 주소 10.10.20.5와 요청 내용 GET /portal을 그대로 읽을 수 있었다. 두 번째 코드는 실제 암호화 대신 예시 문자열로 안쪽 내용을 바꾸어, 암호화된 내용은 중간에서 읽을 수 없다는 상황을 보여 준다. 터널은 패킷을 감싸는 것이고 내용을 숨기는 것은 암호화라는 차이가 코드로 드러나 기억에 남는다.

## 3교시 · 두 가지 VPN

### 문제 3-1 · 상황에 맞는 VPN 고르기

- (가) ① ~ ④ 의 답을 적어 주세요.
  - 쓸 내용: 「①: … / ②: …」처럼 네 개. 답은 Site-to-Site · Remote Access · 회사 VPN 아님 가운데 하나
  - 답: ①: Remote Access VPN / ②: Remote Access VPN / ③: Site-to-Site VPN / ④: 회사 VPN 아님.
- (나) 풀이 예제는 왜 Site-to-Site VPN 이고 ① 은 왜 Remote Access VPN 인지, 두 근거를 비교해 주세요.
  - 쓸 내용: ① 연결 대상이 무엇인지 ② VPN 연결을 시작하는 장비와 직원이 하는 일 — 안내 3.1 표의 줄을 근거로
  - 답: 풀이 예제는 본사 망과 지점 망을 연결하고, 양쪽 VPN 게이트웨이가 연결을 맺으므로 Site-to-Site VPN이다. 직원 PC에는 VPN 프로그램을 설치하거나 직원이 직접 로그인할 필요가 없다. 반면 ①은 직원 노트북 한 대를 회사 망에 연결하고, 직원이 PC의 VPN 클라이언트를 켜고 로그인해 연결을 시작하므로 Remote Access VPN이다. 따라서 장소나 프로그램 설치 유무만으로 판단하기보다, 연결 대상이 망과 망인지 기기 한 대와 회사 망인지와 연결을 시작하는 장비를 함께 확인해야 한다.
- (다-1) 🔍 ④ 처럼 회사 노트북에서 상용 VPN 앱이 켜져 있으면, 관제 담당자에게 무엇이 문제일까요?
  - 쓸 내용: ① 상용 VPN 터널의 끝이 어디인지 ② 회사 방화벽 · DNS 서버가 그 노트북의 목적지와 내용을 볼 수 있는지 ③ 그래서 회사가 무엇을 못 하게 되는지
  - 답: 상용 VPN 터널의 끝은 회사 VPN 게이트웨이가 아니라 VPN 업체의 서버이다. 회사 방화벽을 지나는 트래픽이 이 터널로 전달되면 방화벽에는 업체 서버와의 암호화된 통신이 보여, 터널 안의 실제 목적지와 내용을 확인하기 어려워진다. DNS 질의도 터널을 통해 업체 쪽으로 보내면 회사 DNS 서버의 기록·차단을 거치지 않을 수 있다. 따라서 회사의 위험 사이트 차단이나 정보 유출 탐지에 빈틈이 생길 수 있다. 처음에는 업체로 회사 데이터가 유출될 위험만 생각했지만, 관제에서는 회사의 관찰·통제가 어려워진다는 점도 중요하다. 다만 업체 서버를 거친다는 사실만으로 회사 데이터가 실제 유출됐다고 확정할 수는 없다.
- (다-2) 지점이 3곳에서 30곳으로 늘었습니다. 지점 직원 300명이 모두 Remote Access VPN 을 쓰게 하는 것과 비교하면, Site-to-Site VPN 의 좋은 점은 무엇일까요?
  - 쓸 내용: ① 지점 30곳일 때와 직원 300명일 때의 VPN 연결 수를 숫자로 ② 직원이 해야 할 일이 어떻게 다른지 ③ 관리하는 사람에게 무엇이 달라지는지 한 가지
  - 답: 수업의 본사와 각 지점을 연결하는 구조에서 Site-to-Site VPN은 지점 30곳에 연결 30개를 관리하지만, Remote Access VPN은 직원 300명이 동시에 접속하면 PC마다 하나씩 연결 300개를 관리한다. Site-to-Site에서는 양쪽 VPN 게이트웨이가 연결을 유지하므로 직원이 각자 VPN 클라이언트를 설치하고 접속할 때마다 로그인할 필요가 없다. 관리자는 개별 PC의 VPN 설치와 접속 문제를 지원하는 부담을 줄이고 지점 게이트웨이 중심으로 연결을 관리할 수 있다. 처음에는 연결 후 모니터링만 하면 된다고 썼지만, 게이트웨이 설정·업데이트·인증서·접근 정책과 장애 대응은 계속 관리해야 한다.

### 문제 3-2 · 출발지 주소로 VPN 직원 · 지점 · 본사 가리기

- (가) ① ~ ⑤ 의 판정을 적어 주세요.
  - 쓸 내용: 「① … / ② … / ③ … / ④ … / ⑤ …」처럼 다섯 개. 답은 VPN 직원 · 지점 PC · 본사(PC · 서버) · 목록에 없는 주소 가운데 하나
  - 답: ①: VPN 직원 / ②: 지점 PC / ③: 본사(PC・서버) / ④: 목록에 없는 주소 / ⑤: 목록에 없는 주소. ③의 10.10.20.5는 본사 범위 10.10.0.0/16에 속하며, 수업 예시에서는 업무 포털 서버이다.
- (나) 🔍 ④ `10.8.1.7` 은 `10.8` 로 시작하는데 왜 VPN 직원이 아닐까요?
  - 쓸 내용: ① VPN 주소 풀 `10.8.0.0/24` 의 처음 ~ 끝 주소 ② `10.8.1.7` 이 그 범위에 들어 있는지
  - 답: VPN 주소 풀 10.8.0.0/24의 전체 주소 범위는 10.8.0.0~10.8.0.255이다. /24는 앞의 24비트, 즉 앞 세 숫자가 망 부분이므로 10.8.0과 같은지 비교한다. 10.8.1.7은 세 번째 숫자가 1이어서 이 범위를 벗어나므로, 수업의 회사 주소 표에서는 VPN 직원이 아니라 목록에 없는 주소로 분류한다. 10.8로 시작한다는 사실만으로 같은 VPN 주소 풀이라고 판단하면 안 된다.
- (다) 본사 서버 로그에 출발지 `10.20.5.3` 이 보였습니다. 세 범위 어디에도 들어 있지 않습니다. 어떤 경우를 의심해 볼 수 있을까요?
  - 쓸 내용: ① 이 주소가 사설 주소인지 공인 주소인지와, 그래서 어디쯤에서 온 것인지 ② 의심할 수 있는 경우 두 가지 이상
  - 답: 10.20.5.3은 사설 범위 10.0.0.0~10.255.255.255에 속하므로 공인 IP가 아니라 사설 IP이다. 수업 상황에서는 회사 내부나 연결된 사설망 쪽에서 온 주소로 의심할 수 있지만, 주소만으로 정확한 장비 소속이나 접속 경로를 확정할 수는 없다. 회사 주소 표에 아직 반영하지 않은 새 지점·서브넷, 허가 없이 연결한 장비, IP 설정 오류 등을 확인해야 한다. 처음에는 회사 목록에 없으므로 공인 IP라고 생각했지만, 사설·공인 구분과 회사 목록의 등록 여부는 별개이다. 따라서 회사의 주소 배정 정보와 라우팅·접속 로그를 대조하고, 목록에 없다는 이유만으로 개인 PC나 해킹 시도라고 단정하지 않는다.

### 이 교시에 새로 안 것

- 이 교시에서 새로 알게 된 것 하나를 적어 주세요. (「이 교시에 새로 안 것」 칸)
  - 쓸 내용: 새로 안 것 하나와, 그게 왜 기억에 남는지
  - 답: 사설 IP인지와 회사 주소 목록에 등록되어 있는지는 별개의 기준이라는 것을 새로 알게 됐다. 처음에는 회사 목록에 없는 10.20.5.3을 공인 IP라고 생각했지만, 이 주소도 사설 범위인 10.0.0.0~10.255.255.255 안에 들어간다. 또한 10.8.1.7은 10.8로 시작해도 회사 VPN 주소 풀 10.8.0.0/24의 범위인 10.8.0.0~10.8.0.255에는 포함되지 않는다. 익숙한 앞자리나 회사 목록만 보고 판단하지 않고, 사설 주소 범위와 회사에서 정한 서브넷 범위를 각각 확인해야 한다는 점이 기억에 남는다.

### 문제 4-1 · 한 IP 에서 여러 계정이 실패한 로그인 찾기

- (가-1) `day04_4-1_spray_3.py` 를 실행했을 때 나온 줄을 그대로 옮겨 적어 주세요.
  - 쓸 내용: 터미널 출력 줄을 복사해 붙여 넣기
  - 답: 185.220.101.4 4 ['kim', 'lee', 'park', 'choi']
- (가-2) `day04_4-1_spray_2.py` 에서 새로 나온 줄을 적어 주세요.
  - 쓸 내용: 첫 파일에는 없고 두 번째 파일에만 나온 줄 하나
  - 답: 45.155.205.9 2 ['han', 'seo']
- (나) 🔍 `185.220.101.4` 에서는 계정마다 실패가 한 번씩뿐입니다. 이것이 한 계정이 여러 번 실패하는 경우보다 위험하게 볼 수 있는 이유는 무엇일까요?
  - 쓸 내용: ① 계정 잠금이 무엇을 세는지(안내 4.1 의 말) ② 이 IP 의 공격이 그 기준에 걸리는지 ③ 하나만 맞으면 어떻게 되는지
  - 답: 수업에서 설명한 계정 잠금은 한 계정의 로그인 실패 횟수를 세고, 정해진 횟수 이상 실패하면 해당 계정을 잠근다. 185.220.101.4에서는 서로 다른 네 계정에 한 번씩만 실패했으므로, 계정마다 여러 번 실패해야 하는 잠금 기준을 피할 수 있다. 여러 계정에 흔한 비밀번호를 조금씩 시도하는 비밀번호 스프레이가 의심되는 패턴이며, 한 계정이라도 인증에 성공하면 공격자가 그 계정의 권한으로 접근할 위험이 있다. 다만 이 코드의 로그에는 시도한 비밀번호가 없으므로, 이 패턴만으로 같은 비밀번호를 사용한 공격이라고 확정할 수는 없다.
- (다-1) `121.134.5.9` 의 `lee` 는 실패 두 번 뒤에 성공했습니다. 이 코드는 이 줄을 찾지 못합니다. 왜일까요? 이 줄은 확인해야 할까요?
  - 쓸 내용: ① 코드가 세는 것(계정 수)과 `lee` 의 계정 수 ② 4.1 표에서 이 줄에 해당하는 신호 ③ 확인 여부와 그렇게 판단한 이유
  - 답: 코드는 IP별로 로그인에 실패한 서로 다른 계정 수를 세며, 같은 계정은 목록에 한 번만 넣는다. 따라서 121.134.5.9의 lee는 두 번 실패해도 계정 수가 1개여서 기준 3개와 2개 모두에 걸리지 않고, success 기록은 집계하지 않으므로 실패 뒤 성공하는 순서도 탐지하지 못한다. 하지만 이 기록은 수업 표의 실패 뒤 성공에 해당하므로 확인해야 한다. 비밀번호를 알아낸 공격일 수도 있고 정상 사용자가 오타를 고친 것일 수도 있어, 평소 접속 IP와 이전 로그인 기록 등을 함께 대조해야 한다. 실패 횟수와 서로 다른 계정 수는 구분해서 봐야 한다.
- (다-2) 기준을 2개로 낮추면 정상 직원이 걸릴 수도 있습니다. 어떤 경우일지 한 가지 적어 주세요.
  - 쓸 내용: 같은 공인 IP 를 여러 직원이 쓰는 경우 등 한 가지와, 왜 정상인데 걸리는지
  - 답: 같은 사무실이나 카페에서 정상 직원 두 명이 PAT를 통해 공인 IP 하나를 공유하는 경우가 있다. 두 사람이 각자 자기 계정의 비밀번호를 잘못 입력하면, 외부 로그에는 한 IP에서 서로 다른 계정 두 개의 로그인이 실패한 것으로 보인다. 기준을 2개로 낮추면 이 정상적인 오타도 공격 의심으로 출력될 수 있으며, 이런 경우를 오탐이라고 한다. 따라서 기준을 낮추면 놓치는 의심 패턴을 줄일 수 있지만 오탐도 늘 수 있어, 공인 IP 공유 여부와 로그인 전후 기록을 함께 확인해야 한다.

### 문제 4-2 · VPN 로그인 뒤에 일어난 일 읽기

- (가) VPN 게이트웨이가 `kim` 의 로그인을 확인한 시각과 횟수, 그 뒤 사내 접속 세 줄의 목적지 포트를 적어 주세요.
  - 쓸 내용: 시각 하나와 횟수 하나, 포트 번호 세 개
  - 답: 로그인 확인 시각: 09:02 / VPN 로그인 인증: 1번 / 이후 사내 접속의 목적지 포트: 09:05 업무 포털 443, 09:40 관리 서버 SSH 22, 09:41 고객 DB 3306.
- (나) 🔍 영업 담당 `kim` 이 쓸 일이 없는 관리 서버와 고객 DB 접속까지 모두 「허용」된 이유는 무엇일까요?
  - 쓸 내용: ① VPN 이 확인하는 때와 횟수 ② 사내 방화벽이 VPN 주소를 어떻게 대하는지 — 「경계 기반 보안」을 근거로
  - 답: 이 수업 상황에서는 VPN 게이트웨이가 09:02 로그인할 때 한 번 인증하고, 사내 방화벽은 출발지가 VPN 주소이면 내부 사용자로 신뢰해 모두 허용했다. 경계를 통과하면 믿는다는 경계 기반 보안 때문에 영업 담당 kim의 업무에 필요한지는 확인하지 않고 관리 서버와 고객 DB까지 통신을 허용한 것이다. 처음에는 각 부서 PC에 방화벽 규칙을 설정하지 않은 문제라고 생각했지만, 핵심은 사내 방화벽에서 VPN 사용자의 업무와 목적지 서버에 따라 접근을 제한하지 않았다는 점이다. VPN 로그인 인증과 로그인 뒤 서버별 접근 허용은 구분해야 한다.
- (다-1) 09:02 의 로그인이 사실은 `kim` 의 비밀번호를 훔친 공격자였다면, 이 기록에서 공격자는 무엇을 할 수 있었을까요?
  - 쓸 내용: 공격자가 접속할 수 있었던 곳과, 그곳에서 할 수 있는 일 두 가지 이상
  - 답: 공격자는 kim 계정으로 VPN에 로그인해 10.8.0.21을 받은 뒤, 업무 포털 10.10.20.5:443뿐 아니라 관리 서버 10.10.20.9:22와 고객 DB 10.10.30.7:3306으로도 통신을 시도할 수 있었다. 추가로 관리 서버와 DB의 인증을 통과하고 필요한 권한까지 확보했다면 서버 설정 변경이나 고객 정보 조회·유출로 이어질 수 있다. 처음에는 DB 유출이 일어났을 것이라고 단정했지만, 이 기록에서 확인되는 것은 방화벽이 해당 통신을 허용했다는 사실이다. 실제 서버 로그인, 명령 실행, 데이터 조회·유출의 성공 여부는 서버와 DB의 기록 등을 추가로 확인해야 한다.
- (다-2) 위 기록 네 줄이 지나간 장치를 ASCII 아트로 그려 주세요. 장치를 화살표로 순서대로 잇고, 서버 세 곳은 한 곳에서 갈라지게 그립니다. 보고서의 코드 블록 안에 붙여 넣습니다.
  - 쓸 내용: ① 장치 순서(PC → 두 장치 → 서버) ② 갈라지는 서버 세 곳과 포트 번호 ③ 아래 코드 블록 안에 그림을 붙이기
  - 답: 아래 그림처럼 PC에서 VPN 게이트웨이와 사내 방화벽을 거친 뒤 서버 세 곳으로 갈라진다. 대괄호의 허용은 수업의 사내 방화벽 로그에 기록된 판정이며, 서버 자체 인증의 성공을 뜻하지는 않는다.

  - 쓸 내용: 새로 안 것 하나와, 그게 왜 기억에 남는지
  - 답: VPN 로그인 인증과 로그인 뒤 서버에 접근해도 되는지 판단하는 것은 별개라는 것을 새로 알게 됐다. kim이 VPN에 로그인한 뒤 업무와 무관한 관리 서버와 고객 DB까지 허용된 기록을 보면서, 회사 망에 들어왔다는 이유만으로 모든 서버를 신뢰해서는 안 된다는 점이 기억에 남았다. 또한 로그인 실패 횟수와 실패한 서로 다른 계정 수를 구분해야 하며, 같은 공인 IP를 공유하는 정상 직원들의 오타도 공격 의심으로 잡힐 수 있다는 것을 알게 됐다. 앞으로는 VPN 로그인과 이후 접속 기록을 이어 보고, 방화벽의 허용 기록만으로 서버 로그인이나 데이터 유출까지 성공했다고 단정하지 않아야겠다.
