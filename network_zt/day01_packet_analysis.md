## 2교시 · ping

### 문제 2-1 · 결과 화면 읽기

- 보냄 · 받음 · 손실 · 평균: 실습 자료의 예시 기준으로 보냄 4개, 받음 3개, 손실 1개(25%), 평균 왕복 시간 47ms.
- 손실 % 는 보낸 수와 받은 수로 어떻게 계산했나요?
  - 답: 보낸 수에서 받은 수를 빼면 응답받지 못한 수가 나온다. 이것을 보낸 수로 나누고 100을 곱했다. 예시에서는 4개를 보내고 3개를 받았으므로 (4 - 3) ÷ 4 × 100 = 25%이다.

### 문제 2-2 · 구글 DNS 서버에 `ping` 열 번 보내기

- `8.8.8.8`까지 측정한 결과:

| 항목 | 결과 |
|---|---|
| 평균 왕복 시간 | 36.375ms ≈ 36.38ms |
| TTL | 115 (모든 응답 동일) |
| 보냄 | 56개 |
| 받음 | 56개 |
| 손실 | 0개 (0%) |

평균은 개별 응답에 표시된 왕복 시간의 합계 2,037ms를 받은 패킷 56개로 나누어 계산했다.

> 측정 범위: 과제는 `ping -n 10 8.8.8.8`로 10회 전송하는 것이지만, 위 수치는 실제로 기록한 `ping 8.8.8.8` 14회 실행(실행당 4개, 총 56개 패킷)을 합산한 결과이다.

### 문제 2-3 · 이름으로 `ping` 보내기

- `google.com`의 IP 주소: 142.250.197.110 (2026-10-12 보고서 보완 시 같은 PC에서 `ping -4 google.com`으로 추가 측정).
- 이름만 입력했는데 IP 주소가 나온 이유는 무엇인가요?
  - 답: DNS가 이름에 대응하는 IP 주소를 찾아 주기 때문이다. 그래서 `google.com`처럼 이름만 입력해도 목적지 IP를 얻은 뒤 그 주소로 ping 요청을 보낼 수 있다.

### 문제 2-4 · 두 가지 실패를 구별하기

- 두 실패 문구와 멈춘 단계:

| 명령 | 실패 문구 | 멈춘 단계 |
|---|---|---|
| `ping abc.nowhere-not-exist` | Ping 요청에서 abc.nowhere-not-exist 호스트를 찾을 수 없습니다. 이름을 확인하고 다시 시도하십시오. | DNS 이름 해석 단계 |
| `ping 192.0.2.1` | 요청 시간이 만료되었습니다. | ICMP Echo Reply(응답)를 기다리는 단계 |

- 두 실패는 각각 어디에서 멈춘 것인가요?
  - 답: `abc.nowhere-not-exist`는 DNS 이름 해석에서 IP 주소를 찾지 못해 멈췄다. 처음에는 Echo 요청을 보내다가 실패한 것으로 생각했지만, 목적지 IP를 얻지 못했으므로 ICMP Echo Request(응답 요청)를 보내기 전 단계에서 실패한 것이다.
  - 답: `192.0.2.1`은 IP를 직접 입력했으므로 DNS 이름 해석이 필요 없다. 요청은 보냈지만 제한 시간 안에 ICMP Echo Reply(응답)가 오지 않아 타임아웃이 발생했다. 처음에는 사설 IP여서 실패한 것으로 생각했지만, 이 주소는 문서·예시용 예약 주소였다. 타임아웃만으로는 목적지가 없는지, 중간에서 차단됐는지, 대상이 응답하지 않은 것인지 알 수 없다.

> `192.0.2.1`은 사설 IP가 아니라 문서·예시용 예약 대역인 TEST-NET-1(`192.0.2.0/24`)에 속한다. 출처: [IANA IPv4 특수 목적 주소 목록](https://www.iana.org/assignments/iana-ipv4-special-registry).

### ⭐ 도전 2-5 · `ping` 결과를 파이썬으로 판정하기

- 출력 결과:

```text
[정상] 8.8.8.8 34ms
[느림] 1.1.1.1 120ms
[실패] 192.0.2.1 응답 없음
```

위 출력은 `ping_check.py`에 미리 입력된 예시 데이터를 판정한 결과이며, 문제 2-2의 실측 평균과는 별개이다.

### 찾아본 것

- 2.1 표에서 찾아 쓴 TTL의 뜻과 라우터를 지날 때 바뀌는 방식: TTL(Time To Live)은 IP 패킷이 거칠 수 있는 남은 홉 수를 제한하는 값이다. 라우터를 하나 지날 때마다 1씩 감소하며, 0이 되면 패킷은 폐기된다. 이번 `ping` 결과의 TTL=115는 수신한 응답 패킷에 남아 있는 값이며, 왕복 시간이나 거쳐 온 라우터 수 자체를 뜻하지 않는다.

### 이 교시에 새로 안 것

- 이 교시에서 새로 알게 된 것:
  - 두 실패 문구를 비교하면서, 이름을 IP로 바꾸지 못한 경우와 요청 후 응답이 오지 않은 경우는 멈춘 단계가 다르다는 것을 알게 됐다.
  - 특히 타임아웃은 Echo 응답이 왔다는 뜻이 아니라, 정해진 시간 안에 응답을 받지 못했다는 뜻이다.
  - 내 `8.8.8.8` 기록에서는 56개 모두 응답을 받았고 손실은 0%였다. 표시된 왕복 시간을 합산해 계산한 평균은 약 36.38ms였다.
  - 응답에 표시된 TTL=115는 남은 홉 수를 나타내며, 거쳐 온 라우터가 115개라는 뜻은 아니라는 것도 알게 됐다.

## 3교시 · IP 와 MAC

### 문제 3-1 · 결과 화면 읽기

- 예시 화면의 IPv4 주소 · MAC 주소 · 기본 게이트웨이:
  - IPv4 주소: 192.168.0.15
  - MAC 주소: A4-B1-C2-D3-E4-F5
  - 기본 게이트웨이: 192.168.0.1

### 문제 3-2 · 내 IP 주소 · 게이트웨이 · MAC 주소 찾기

- 찾은 장치 이름 · 내 IPv4 주소 · 기본 게이트웨이 · MAC 주소(물리적 주소):
  - 찾은 장치 이름: 이더넷 어댑터 이더넷 2
  - 내 IPv4 주소: 192.168.100.107
  - 게이트웨이: 192.168.1.1
  - MAC 주소: D8-BB-C1-40-36-81
  - 서브넷 마스크: 255.255.0.0

내 IP와 게이트웨이는 세 번째 숫자가 다르지만, 확인한 마스크는 `255.255.0.0`이었다. 따라서 같은 서브넷은 `192.168.0.0/16`이고, 내 IP `192.168.100.107`과 게이트웨이 `192.168.1.1`은 이 범위에 함께 들어간다.

### 문제 3-3 · 게이트웨이까지 `ping`

- 게이트웨이까지 평균 · 2-2 의 `8.8.8.8` 평균:
  - 게이트웨이 `192.168.1.1`까지 평균: 0ms (Windows ping 통계 표시값). 최소 0ms, 최대 1ms이며, 개별 응답은 1ms 1개와 1ms 미만 3개였다. 보냄 4개, 받음 4개, 손실 0개(0%).
  - `8.8.8.8`까지 평균: 약 36.38ms (2-2에서 합산한 결과).

> 게이트웨이 값은 2026-10-12 보고서 보완 시 같은 PC(IP `192.168.100.107`, 기본 게이트웨이 `192.168.1.1`)에서 `ping -4 192.168.1.1`로 추가 측정했다. 평균 0ms는 정수로 표시된 통계값이므로 실제 왕복 시간이 전혀 없다는 뜻은 아니다. `8.8.8.8` 값은 앞서 기록한 측정 결과이다.
- 게이트웨이까지가 더 짧은 이유는 무엇인가요?
  - 답: 게이트웨이가 더 가까이 있기 때문이라고 생각했다. 실제로 게이트웨이까지는 대부분 1ms 미만으로 응답했고, 앞서 측정한 `8.8.8.8`의 평균은 약 36.38ms였다. 게이트웨이는 같은 내부망에 있고, `8.8.8.8`까지는 외부 인터넷의 여러 라우터와 회선을 거쳐야 하므로 게이트웨이까지의 왕복 시간이 더 짧게 나온 것으로 이해했다.

### 문제 3-4 · ARP 캐시 보기 — `arp -a`

- 게이트웨이 줄의 MAC 주소 · 유형:
  - IP 주소: 192.168.1.1
  - MAC 주소: 00-10-f3-a3-fc-96
  - 유형: 동적
- 🔍 ARP 는 무엇을 알아내려고 쓰나요? 내 결과의 게이트웨이 줄을 예로 들어 설명합니다.
  - 답: MAC 주소를 알아내기 위해 사용한다. 정확히는 같은 망에서 특정 IP 주소에 대응하는 MAC 주소를 찾는 것이다. 내 ARP 표에서는 게이트웨이 `192.168.1.1`에 대응하는 MAC 주소가 `00-10-f3-a3-fc-96`으로 저장되어 있었다.

### ⭐ 도전 3-5 · 주소 모양으로 IP 와 MAC 구별하기

- 출력 결과:
  ```text
  IP 192.168.0.15
  MAC a8-5e-45-01-2b-3c
  MAC ff-ff-ff-ff-ff-ff
  모름 192.168.0
  ```

점으로 나눈 조각이 4개인 주소는 IP, 하이픈으로 나눈 조각이 6개인 주소는 MAC으로 분류했다. 여기서는 주소의 모양을 구별한 것이며, 실제로 존재하는 장치인지 확인한 것은 아니다.

### 이 교시에 새로 안 것

- 이 교시에서 새로 알게 된 것:
  - IP 주소와 MAC 주소가 서로 다른 역할을 한다는 것을 내 PC의 주소와 게이트웨이의 ARP 항목을 통해 확인했다. ARP는 같은 망에서 IP에 대응하는 MAC 주소를 알아내는 데 쓰인다.
  - ARP의 `동적`과 DHCP의 자동 IP 배정은 다른 개념이라는 것을 알게 됐다.
  - IP의 앞 세 숫자만 보고 같은 망인지 판단하면 안 되고, 서브넷 마스크도 함께 봐야 한다. 내 마스크는 `255.255.0.0`이라 `192.168.100.107`과 `192.168.1.1`이 같은 서브넷에 속한다.
  - ARP 표에 보이는 장치 수만으로 학원의 출석 인원이나 켜져 있는 컴퓨터 수를 정확히 알 수는 없다는 것도 배웠다.

### 문제 4-1 · 직접 실행해 보기

- `3389` 는 사전에 없는데도 에러 없이 둘째 줄이 나온 이유는 무엇인가요?
  - 답: 처음에는 `.get()`이 예외처리를 해 주기 때문이라고 생각했다. 정확히는 `.get(3389, "모름")`이 사전에 3389라는 키가 없으면 지정한 기본값인 `"모름"`을 반환하기 때문이다. 그래서 `PORTS[3389]`처럼 직접 조회할 때 발생하는 `KeyError` 없이 둘째 줄이 출력된다.

### 문제 4-2 · 지금의 연결 보기 — `netstat -n`

- 고른 줄의 외부 포트 → 서비스 이름:
  - 443 → HTTPS

  ```text
  활성 연결

    프로토콜  로컬 주소           외부 주소              상태
    TCP    192.168.100.107:50047  172.217.114.4:443      ESTABLISHED
  ```

외부 주소의 `:` 뒤 숫자 443을 실습 자료의 포트 표와 대조해 HTTPS로 분류했다. 내 쪽 포트 50047은 이 연결에 쓰인 임시 포트이며, 서비스 이름을 찾을 때는 상대 쪽 포트 443을 확인했다.

### 문제 4-3 · 그 연결은 어느 프로그램의 것인가

- PID → 프로그램 이름: 6512 → GoogleDriveFS.exe

내가 기록한 연결의 PID와 프로그램 이름이다. 보고서 검수 시에도 PID 6512의 프로세스 이름은 `GoogleDriveFS`로 확인됐다. 다만 4-2의 연결은 검수 시점에 목록에서 사라져, 해당 연결과 PID의 대응은 당시 내가 기록한 결과를 기준으로 남겼다.

### 문제 4-4 · 내 PC 의 LISTENING 포트 찾기

- 4.1 표에 있는 LISTENING 포트 → 서비스 이름:
  - 135 → RPC (Windows 원격 기능 호출)
  - 445 → SMB (Windows 파일·프린터 공유)
  - 3389 → RDP (Windows 원격 데스크톱)

2026-10-12 보고서 보완 시 같은 PC에서 `netstat -ano`로 확인한 LISTENING 줄 중 4.1 표에 있는 포트를 골랐다. 아래의 맨 끝 숫자는 PID이다.

```text
TCP    0.0.0.0:135    0.0.0.0:0    LISTENING    1788
TCP    0.0.0.0:445    0.0.0.0:0    LISTENING    4
TCP    0.0.0.0:3389   0.0.0.0:0    LISTENING    6856
```

- 🔍 LISTENING 과 ESTABLISHED 는 무엇이 다른가요? 4-2 와 4-4 에서 본 줄을 예로 들어 설명합니다.
  - 답: LISTENING은 내 PC의 프로그램이 연결 요청을 기다리는 상태이고, ESTABLISHED는 상대와 TCP 연결이 맺어진 상태이다. 4-4의 `0.0.0.0:445`는 내 PC가 445번 포트에서 연결 요청을 기다린다는 뜻이다. 반면 4-2의 `192.168.100.107:50047 → 172.217.114.4:443` 줄은 내 PC와 상대의 443번 포트 사이에 연결이 이미 맺어져 있음을 보여 준다. 같은 PC에서도 연결을 기다리는 포트와 이미 연결된 통신이 함께 존재할 수 있다는 것을 알게 됐다.

> `0.0.0.0`은 모든 로컬 IPv4 주소에서 연결을 기다린다는 뜻이다. LISTENING이라고 해서 외부 인터넷에서 실제로 접속할 수 있다는 뜻은 아니며, 접속 가능 여부는 방화벽과 네트워크 설정에도 영향을 받는다. ESTABLISHED도 연결이 맺어졌다는 뜻이며, 그 순간 계속 데이터를 주고받고 있다는 뜻은 아니다.

### 문제 4-5 · 증상으로 층 좁히기

- 증상 ① · ② · ③에서 의심되는 층:
  - ① IP로 ping은 되는데 이름으로는 호스트를 찾지 못함: 7층 응용 계층의 DNS 이름 해석 문제.
  - ② 기본 게이트웨이 ping 타임아웃: 내부망의 1~3층 문제를 우선 의심.
  - ③ ping은 되는데 특정 웹 사이트만 열리지 않음: 4층 이상의 포트나 웹 서비스 문제를 의심.

- 증상마다 그렇게 판단한 근거는 무엇인가요?
  - 답 ①: 처음 생각한 것처럼 DNS 문제를 의심할 수 있다. `8.8.8.8`에는 ping이 되므로 해당 IP까지 요청과 응답이 오가는 경로는 동작한다. 반면 `google.com`은 IP 주소를 얻지 못해 요청을 보내기 전에 실패했으므로, 이름 해석을 담당하는 DNS를 먼저 확인해야 한다. DNS는 OSI 모델에서 7층 응용 계층에 해당한다.
  - 답 ②: 처음에는 ARP 과정의 데이터링크 문제라고 생각했다. 하지만 게이트웨이에서 응답이 오지 않았다는 것만으로 ARP 문제라고 확정할 수는 없다. 랜선이나 Wi-Fi 같은 1층, 스위치나 ARP 같은 2층, IP·서브넷 마스크·게이트웨이 설정 같은 3층을 차례로 확인해야 한다. 문제의 조건에는 다른 목적지로 ping이 성공했다는 정보도 없다. 게이트웨이가 ICMP 응답을 차단한 경우에도 타임아웃이 날 수 있으므로, 내부망 문제를 의심하되 추가 확인이 필요하다.
  - 답 ③: 상대 서버나 포트 문제를 의심한 방향은 맞지만, 포트 번호는 7층이 아니라 4층에 해당한다. ping이 성공했다는 것은 ICMP 요청과 응답이 오갔다는 뜻이며, 웹 접속에 필요한 TCP 연결이나 HTTPS 통신까지 성공했다는 뜻은 아니다. 따라서 TCP 포트와 방화벽, TLS 설정, 웹 서버 상태 등을 확인해야 한다. 포트가 닫혀 있을 가능성은 있지만, 이 증상만으로 그것이 원인이라고 확정할 수는 없다.

### 찾아본 것

- 4.1 표에서 찾아 쓴 3389의 위험과 445를 이용해 퍼진 랜섬웨어:
  - 3389는 Windows 원격 데스크톱(RDP)에 쓰이는 포트이다. 인터넷에서 접속할 수 있게 노출하면 비밀번호 추측이나 유출된 계정 정보, 취약점을 이용한 침입 시도의 대상이 될 수 있다. 필요 없는 원격 접속은 끄고, 필요한 경우에도 접속 범위와 인증을 관리해야 한다. 내 PC에서도 3389가 LISTENING으로 보였지만, 그것만으로 인터넷에 공개되어 있다고 판단할 수는 없다. 출처: [CISA 랜섬웨어 예방 가이드](https://www.cisa.gov/stopransomware/ransomware-guide).
  - 445는 Windows 파일·프린터 공유에 쓰이는 SMB의 TCP 포트이다. 대표적인 사례인 WannaCry(워너크라이, WannaCrypt)는 패치되지 않은 SMBv1의 취약점을 EternalBlue로 악용해 다른 컴퓨터로 퍼졌다. 445번 포트가 있다는 사실 자체가 감염을 뜻하는 것은 아니며, 취약한 SMB 서비스와 보안 업데이트 여부가 중요하다. 출처: [Microsoft의 WannaCrypt 분석](https://www.microsoft.com/en-us/security/blog/2017/05/12/wannacrypt-ransomware-worm-targets-out-of-date-systems/).

### 이 교시에 새로 안 것

- 이 교시에서 새로 알게 된 것:
  - 처음에는 포트 번호를 7층으로 생각했지만, TCP·UDP의 포트는 4층에서 사용하는 번호라는 것을 알게 됐다. 서비스 이름을 찾을 때는 내 쪽 임시 포트와 상대 쪽 서비스 포트를 구분해야 한다.
  - LISTENING은 새 연결을 기다리는 상태이고, ESTABLISHED는 상대와 TCP 연결이 맺어진 상태이다. 서버는 여러 클라이언트를 받기 위해 LISTENING 소켓을 유지하면서, 받아들인 연결마다 별도의 ESTABLISHED 소켓을 만들 수 있다.
  - 서버의 포트가 같아도 클라이언트의 IP와 포트가 다르면 연결을 구별할 수 있다. 접속을 거는 클라이언트는 LISTENING을 거치지 않고 연결을 시작한다.
  - netstat의 PID와 프로세스 목록을 연결하면 그 통신을 하는 프로그램을 찾을 수 있다. 내가 기록한 예시는 6512 → GoogleDriveFS.exe였다.
  - ping이 된다고 웹 사이트까지 반드시 열리는 것은 아니다. DNS 이름 해석, TCP 포트, TLS, 웹 서비스 등 어느 단계에서 막혔는지 나누어 생각해야 한다.
  - 포트가 LISTENING이라는 사실과 인터넷에서 실제로 접속 가능한지는 다르다. 원격 접속과 파일 공유는 편리하지만, 노출 범위와 보안 업데이트도 함께 확인해야 한다.

## 5교시 · TCP

### 문제 5-1 · 직접 실행해 보기

- 출력 세 줄:

```text
True
False
443
```

실습 자료의 코드에서 `"ACK" in packet["flags"]`, `packet["flags"] == "ACK"`, `packet["dst_port"]`를 차례로 출력한 결과이다.

- 탐지 코드에서 플래그를 `==` 로 검사하면 어떤 일이 생기나요? 둘째 줄을 근거로 설명합니다.
  - 답: `packet["flags"]`는 리스트이므로 문자열 `"ACK"`와 같지 않다. 실제로 리스트 안에 ACK가 있어도 둘째 줄은 `False`가 나와, `== "ACK"`로 검사하면 ACK 플래그를 탐지하지 못한다. 원소가 하나인 `["ACK"]`도 리스트이기 때문에 문자열 `"ACK"`와는 다르다. 이 코드처럼 플래그를 리스트로 저장했다면 `"ACK" in packet["flags"]`로 포함 여부를 확인해야 한다.

### 문제 5-2 · TCP 일까 UDP 일까

- ① ~ ⑤ 가 각각 TCP · UDP · ICMP 중 무엇인지:
  - 답: 실습 자료의 분류 기준으로 ① 사진 파일 보내기 → TCP, ② 실시간 방송 보기 → UDP, ③ `requests.post`로 LLM 부르기 → TCP, ④ DNS 조회 → UDP, ⑤ ping → ICMP이다.
- ① 사진 파일 보내기가 TCP 인 이유는 무엇인가요?
  - 답: 사진 파일은 데이터 일부가 빠지면 파일이 깨지거나 원래 내용과 달라질 수 있기 때문이다. TCP는 전달 확인과 재전송, 순서 정리를 통해 빠진 데이터 없이 전달하도록 하므로 사진처럼 온전한 데이터가 필요한 전송에 적합하다. 여기서 안전하다는 것은 전달의 신뢰성을 뜻하며, TCP 자체가 암호화를 제공한다는 뜻은 아니다.

> 위 분류는 실습 자료의 예시이다. 실제 스트리밍이나 DNS의 사용 프로토콜은 서비스와 설정에 따라 달라질 수 있으므로, 모든 방송이 UDP이고 모든 DNS가 UDP라고 단정하지 않는다.

### 문제 5-3 · 세 번의 순서 맞히기

- 세 패킷의 순서와 방향:
  1. (나) `[SYN]`: 내 PC → 서버. 연결을 시작하자고 요청한다.
  2. (다) `[SYN, ACK]`: 서버 → 내 PC. 내 PC의 SYN을 확인하고, 서버 쪽 SYN도 함께 보낸다.
  3. (가) `[ACK]`: 내 PC → 서버. 서버의 SYN을 확인한다.

- 🔍 연결을 맺을 때는 세 번인데, 끝낼 때는 왜 네 번인가요?
  - 답: 처음에는 연결할 때 보낼 데이터가 없어서 연결 요청과 확인을 한 번에 보낸다고 생각했다. 더 정확히는 서버가 내 SYN에 대한 ACK와 자신의 SYN을 한 패킷에 담아 보내므로 연결 과정이 세 번이 된다. 종료할 때는 양쪽이 각자의 송신을 끝내고 확인받아야 한다. 상대의 FIN을 확인하는 ACK를 보낸 뒤에도 내 쪽에 보낼 데이터가 남아 있을 수 있어, 내 FIN은 나중에 따로 보낼 수 있다. 그래서 보통 FIN → ACK → FIN → ACK의 네 단계로 설명한다. 다만 ACK와 FIN이 한 패킷에 합쳐지는 경우도 있어 항상 패킷 네 개로 끝나는 것은 아니다.

참고: [RFC 9293 — TCP 연결과 종료](https://www.rfc-editor.org/rfc/rfc9293.html).

### 문제 5-4 · 같은 서버로 간 두 연결은 무엇이 다른가

- 두 연결에서 같은 것 · 다른 것:
  - 실습 자료의 예시 기준으로 같은 것은 내 IP `192.168.0.15`, 서버 IP `142.250.196.110`, 서버 포트 `443`, 프로토콜 TCP, 상태 ESTABLISHED이다.
  - 다른 것은 내 PC의 임시 포트로, 첫 번째 연결은 `51234`, 두 번째 연결은 `51240`이다. 이 주소와 포트는 실습 자료의 예시이며 내 PC의 실측값은 아니다.
- 같은 서버로 간 두 연결을 무엇으로 구별하나요?
  - 답: 이 예시에서는 클라이언트의 포트 번호로 구별한다. 정확히는 TCP 연결을 출발지 IP·출발지 포트·목적지 IP·목적지 포트의 네 값으로 구별한다. 여기서는 내 IP와 서버 IP·포트가 모두 같고, 내 쪽 임시 포트만 달라 두 연결을 구별할 수 있다.

### 이 교시에 새로 안 것

- 이 교시에서 새로 알게 된 것:
  - 리스트와 문자열은 원소가 하나여도 서로 다르다. 플래그를 리스트로 저장한 코드에서는 `==`로 문자열과 비교하면 플래그를 놓칠 수 있어, `in`으로 포함 여부를 확인해야 한다.
  - TCP는 전달 확인과 재전송, 순서 정리를 제공한다. 사진 파일처럼 데이터가 온전히 필요한 전송에 적합하며, 이것은 암호화와는 다른 의미이다.
  - TCP 연결은 SYN → SYN·ACK → ACK로 시작한다. 서버가 확인과 자신의 연결 요청을 함께 보내는 것이 세 번이 되는 이유이다.
  - 종료할 때는 상대의 종료 요청을 확인한 뒤에도 내 쪽에서 보낼 데이터가 남아 있을 수 있다. 양쪽의 송신 종료가 따로 이루어지므로 보통 네 단계로 설명하지만, 실제 패킷 수는 달라질 수 있다.
  - 같은 서버의 443번 포트로 여러 연결을 만들어도 내 쪽 임시 포트가 달라 구별할 수 있다. 일반적으로 TCP 연결은 양쪽 IP와 포트 네 값으로 식별한다.
  - ping은 TCP나 UDP가 아니라 ICMP를 사용한다. TCP의 포트나 연결 절차를 ping에 그대로 적용하면 안 된다.

### 실습 2 · 패킷 내용을 해석하고 필터로 확인하기

#### 문제 6-3 · 패킷 하나를 층별로 펼치기

- 선택한 패킷의 상세 값:

| 계층 | 항목 | 기록한 값 |
|---|---|---|
| 2층 Ethernet | Source MAC | 00:10:f3:a3:fc:96 |
| 3층 IPv4 | Source IP | 104.20.23.243 |
| 3층 IPv4 | Destination IP | 192.168.100.107 |
| 3층 IPv4 | Time to Live | 52 |
| 4층 TCP | Source Port | 443 |
| 4층 TCP | Destination Port | 52945 |
| 4층 TCP | Flags | ACK |

추가로 Info에는 `Seq=1 Ack=67 Win=16 Len=0`이 표시됐다. 이 값들은 플래그와 별도의 정보이며, `Len=0`은 이 TCP 세그먼트에 데이터가 없다는 뜻이다. 패킷 전체 길이가 0이라는 뜻은 아니다.

- 이 패킷은 내 PC 가 보낸 것인가요, 받은 것인가요? 어떻게 알았나요?
  - 답: 내 PC가 받은 패킷이다. 목적지 IP가 오전에 확인한 내 IP `192.168.100.107`이고, 서버 쪽 포트 443에서 내 임시 포트 52945로 왔기 때문이다. 처음에는 443 → 숫자이므로 응답이라고만 생각했는데, 이 패킷은 웹 응답 본문이 아니라 ACK 확인 패킷이었다.

Source MAC은 오전에 확인한 게이트웨이의 MAC `00-10-f3-a3-fc-96`과 같은 값이다. 외부 서버에서 온 IP 패킷을 같은 링크의 게이트웨이가 내 PC로 전달했으므로, Source IP는 외부 서버인데 Ethernet의 Source MAC은 게이트웨이로 보인다. 이를 통해 IP는 통신 상대를, MAC은 현재 링크의 전달 장비를 가리킨다는 차이를 확인했다.

#### 문제 6-4 · 필터 결과와 뜻 비교하기

- 같은 캡처에서 기록한 전체 Packets와 필터별 Displayed:

| 표시 필터 | 개수 | 의미 |
|---|---|---|
| 전체 Packets | 589 | 캡처한 전체 패킷 수 |
| `dns` | 32 | DNS로 해석된 패킷 수 |
| `udp` | 468 | UDP를 포함한 패킷 수 |
| `tcp.port == 443` | 67 | 출발지 또는 목적지 TCP 포트가 443인 패킷 수 |

- 필터를 걸어도 `Packets` 는 그대로인데 `Displayed` 만 바뀌는 이유는 무엇인가요?
  - 답: 캡처를 멈춘 뒤 표시 필터를 적용하면 전체 589개는 그대로 보존되고, 그중 필터 조건에 맞는 패킷만 화면에 보이기 때문이다. Displayed는 현재 조건에 맞아 표시된 개수이며, 필터를 지우면 전체 패킷을 다시 볼 수 있다. 표시 필터는 원본 패킷을 삭제하지 않는다.

필터를 적용하면서 직접 확인한 내용:

- `udp`를 적용했는데 Protocol 열에 DNS도 보였다. 이번에 본 DNS 메시지가 UDP 안에 담겨 전송됐기 때문이다.
- `tcp.port == 443`을 적용했는데 TCP와 TLSv1.2가 함께 보였다. TLS 데이터도 TCP 안에 담겨 전송되고, 그 TCP의 출발지나 목적지 포트가 443이면 조건에 맞기 때문이다.
- Protocol 열의 이름 하나가 패킷 안의 모든 계층을 뜻하는 것은 아니다. 표시 필터는 해당 프로토콜이나 필드가 패킷에 있는지 확인하므로, 열에 표시된 이름과 필터 이름이 달라도 정상이다.
- 같은 패킷이 여러 필터에 포함될 수 있고 어느 필터에도 포함되지 않는 패킷도 있으므로, 필터별 개수를 합쳐 전체 589개와 맞출 필요는 없다. DNS가 전부 UDP였는지는 이 숫자만으로 확정할 수 없다.

참고: [Wireshark 공식 문서 — 표시 필터](https://www.wireshark.org/docs/wsug_html_chunked/ChWorkDisplayFilterSection), [필터 표현식](https://www.wireshark.org/docs/wsug_html_chunked/ChWorkBuildDisplayFilterSection).

### 이 교시에 새로 안 것

- 이 교시에서 새로 알게 된 것:
  - Wireshark의 캡처는 화면을 찍는 것이 아니라, 인터페이스를 오가는 패킷을 수집하는 것이다. 이번에는 이더넷 2에서 총 589개를 기록했다.
  - 처음에는 위쪽 기본 열에서 MAC과 TTL도 찾으려 했는데, 이 값은 패킷을 선택한 뒤 아래 상세 창의 Ethernet II와 IPv4를 펼쳐 확인해야 한다는 것을 알게 됐다. 목록의 Length와 IPv4의 TTL은 다른 값이다.
  - 받은 패킷은 목적지 IP가 내 IP인지 확인하면 방향을 더 확실히 판단할 수 있다. 서버 포트 443에서 왔어도 웹 응답 본문이 아니라 ACK 패킷일 수 있다.
  - 외부 서버에서 온 패킷의 Source IP와 Source MAC은 서로 다른 장비를 가리킬 수 있다. 내 기록에서는 Source IP는 외부 서버, Source MAC은 게이트웨이였다.
  - UDP 필터에서 DNS가 보이고 TCP 443 필터에서 TLSv1.2가 보이는 이유는, 하나의 패킷 안에 여러 계층의 프로토콜이 함께 들어 있기 때문이다. 오전에 배운 캡슐화를 실제 패킷으로 확인한 셈이다.
  - 표시 필터는 캡처 원본을 지우지 않고 표시할 패킷만 고른다. 그래서 전체 Packets와 조건별 Displayed를 구분해 기록해야 한다.

## 7교시 · 패킷 분석

### 문제 7-1 · 내 HTTP 연결 하나만 잡기

- 실행한 명령: `curl http://example.com`
- 확인한 연결: `tcp.stream eq 5`, 내 PC `192.168.100.107:56428` ↔ 서버 `172.66.147.243:80`.
- 세 줄 Info의 신호 순서:

| 패킷 번호 | 방향 | Info의 신호 | 의미 |
|---|---|---|---|
| 38 | 내 PC → 서버 | 56428 → 80 [SYN] | 내 PC가 연결을 요청함 |
| 39 | 서버 → 내 PC | 80 → 56428 [SYN, ACK] | 서버가 내 요청을 확인하고 자신의 SYN도 보냄 |
| 40 | 내 PC → 서버 | 56428 → 80 [ACK] | 내 PC가 서버의 SYN을 확인함 |

처음에는 `tcp.flags.syn == 1` 필터에서 SYN과 SYN·ACK만 보였다. SYN이 없는 세 번째 ACK는 이 필터에 맞지 않기 때문이다. 해당 패킷에서 Follow → TCP Stream을 선택하고 창을 닫아 `tcp.stream eq 5`로 같은 연결 전체를 보니 세 패킷을 모두 찾을 수 있었다.

### 문제 7-2 · HTTP 요청과 연결 종료 찾기

- 요청 줄의 Info: 41번 패킷의 `GET / HTTP/1.1`.
- 서버 응답: 46번 패킷의 `HTTP/1.1 200 OK (text/html)`.
- FIN 줄 수: 2줄. 48번은 내 PC → 서버, 50번은 서버 → 내 PC이며 둘 다 `[FIN, ACK]`이다. 51번에서 내 PC가 서버의 FIN을 ACK로 확인했다.

> 실습 자료는 `curl "http://example.com/?q=network_day1"`로 검색어가 포함된 요청을 보내지만, 내가 실행한 명령은 `curl http://example.com`이다. 그래서 실제 화면에는 검색어 없이 `GET / HTTP/1.1`이 보였다. 보고서에는 실제로 확인한 요청을 기록했다.

- 🔍 내 검색어가 그대로 보인 것은 HTTP 이기 때문입니다. 같은 요청을 HTTPS 로 보냈다면 어떻게 보였을까요?
  - 답: 내 화면에서는 검색어 대신 HTTP 요청 줄 `GET / HTTP/1.1`을 평문으로 확인했다. 같은 요청을 HTTPS로 보냈다면 HTTP 요청 경로와 헤더, 본문은 TLS로 암호화되어, 복호화 키가 없는 일반적인 캡처에서는 그대로 읽을 수 없었을 것이다. 다만 IP 주소와 TCP 포트, 연결 상태 같은 정보까지 모두 숨겨지는 것은 아니다.

### 문제 7-3 · 보고서 완성하고 올리기

- 깃허브 `network_zt` 폴더에 보고서가 보이나요: 예 — 업로드 완료로 기록함(사용자의 완료 처리 기준).

### 이 교시에 새로 안 것

- 이 교시에서 새로 알게 된 것:
  - SYN 필터는 SYN과 SYN·ACK만 보여 주므로, 세 번째 ACK까지 보려면 같은 TCP Stream 전체를 확인해야 한다.
  - 연결 시작의 SYN → SYN·ACK → ACK를 실제 패킷 38~40번에서 확인했다. 같은 연결에서도 뒤쪽 ACK는 데이터 수신이나 종료를 확인하는 데 쓰이므로, ACK라고 해서 모두 handshake의 세 번째 패킷은 아니다.
  - HTTP 요청의 `GET / HTTP/1.1`을 읽고 서버의 `200 OK` 응답도 찾았다. 실습 자료의 예시와 다르게 실행했다면 화면에 나온 실제 요청을 기록해야 한다.
  - 종료 플래그는 FIN 단독이 아니라 FIN·ACK로 표시될 수 있다. 내 연결에서는 양쪽이 하나씩 보내 FIN이 있는 패킷이 총 2개였다.
  - HTTPS는 HTTP 내용의 기밀성을 보호하지만, 캡처에서 IP나 포트까지 모두 사라지는 것은 아니라는 것을 알게 됐다.

## 최종 분석 — 7교시에 완성합니다

> 7교시에서 잡은 HTTP 연결 `tcp.stream eq 5`를 처음부터 끝까지 정리한다. 6-3에서 분석한 HTTPS 패킷은 다른 연결이므로 따로 구분했다.

### 1. 연결이 열리는 순간 — 3-way handshake

- 세 줄의 Source → Destination 과 Info:
  - 38번: `192.168.100.107 → 172.66.147.243`, `56428 → 80 [SYN]`.
  - 39번: `172.66.147.243 → 192.168.100.107`, `80 → 56428 [SYN, ACK]`.
  - 40번: `192.168.100.107 → 172.66.147.243`, `56428 → 80 [ACK]`.
- 세 줄이 오간 뒤 두 컴퓨터는 어떤 상태가 되나요?
  - 답: 양쪽이 SYN을 주고받고 확인해 TCP 연결이 맺어진 ESTABLISHED 상태가 된다. 그 뒤 내 PC가 41번 패킷에서 HTTP 요청을 보냈다.

### 2. 패킷 하나를 열어 본 값 — 6-3

- 출발지 · 목적지 IP (3층) · TTL · 출발지 · 목적지 포트 (4층):
  - 7교시 HTTP 요청(41번): 출발지 IP `192.168.100.107`, 목적지 IP `172.66.147.243`, TTL `128`(사용자가 패킷 상세에서 확인), 출발지 포트 `56428`, 목적지 포트 `80`.
  - 6-3의 별도 HTTPS 수신 패킷: 출발지 IP `104.20.23.243`, 목적지 IP `192.168.100.107`, TTL `52`, 출발지 포트 `443`, 목적지 포트 `52945`, Flags `ACK`.
- 목적지 포트를 보고 어떤 서비스로 가는 패킷인지 알 수 있나요? 4.1 표를 근거로 설명합니다.
  - 답: 7교시 요청의 목적지 포트 80은 4.1 표에서 HTTP이다. 실제 Info에도 `GET / HTTP/1.1`이 보여 HTTP 요청임을 함께 확인했다. 반면 6-3의 목적지 포트 52945는 내 PC의 임시 포트이며, 그 패킷은 서버 쪽 443에서 내 PC로 돌아오는 방향이다. 서버 포트와 내 임시 포트를 구분해야 하고, 포트 번호만으로 모든 통신 내용을 확정할 수는 없다.

### 3. HTTP 요청 — 7-2

- 요청 줄에서 그대로 보인 내용:
  - 41번: `GET / HTTP/1.1`. 실행한 요청에 검색어는 포함되지 않았다.
- 이것이 보안에서 문제가 되는 이유는 무엇인가요?
  - 답: HTTP는 요청과 응답을 암호화하지 않아, 통신 경로에서 패킷을 볼 수 있는 사람이 요청 내용을 읽을 수 있기 때문이다. 이번에는 경로 `/`만 보였지만, 검색어나 민감한 정보가 포함된 요청이라면 그 내용도 노출될 수 있다. HTTPS를 사용하면 HTTP 내용을 TLS로 암호화해 이런 노출을 줄일 수 있다.

### 4. 오늘 하루 정리

- 오늘 배운 것 가운데 가장 중요하다고 생각하는 것과 그 이유:
  - 답: 네트워크 문제를 한 가지 원인으로 단정하지 않고, 어느 단계까지 동작했는지 확인하는 것이 중요하다고 생각한다. DNS 이름 해석 실패와 ping 타임아웃은 멈춘 단계가 달랐고, ping이 돼도 웹 서비스가 된다는 뜻은 아니었다. Wireshark에서 IP·MAC·포트와 TCP 연결의 시작·종료를 실제로 확인하면서, 관찰한 값과 추정을 구분해 기록해야 한다는 것도 배웠다.
