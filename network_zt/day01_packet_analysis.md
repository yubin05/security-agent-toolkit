## 2교시 · ping

### 문제 2-1 · 결과 화면 읽기

- 보냄 · 받음 · 손실 · 평균: 실습 자료의 예시 기준으로 보냄 4개, 받음 3개, 손실 1개(25%), 평균 왕복 시간 47ms.
- 손실 % 는 보낸 수와 받은 수로 어떻게 계산했나요?
  - 답: 손실률은 (보냄 − 받음) ÷ 보냄 × 100이다. 예시는 (4 − 3) ÷ 4 × 100 = 25%다.

### 문제 2-2 · 구글 DNS 서버에 `ping` 열 번 보내기

- `8.8.8.8`까지 측정한 결과:

| 항목 | 결과 |
|---|---|
| 평균 왕복 시간 | 36.375ms ≈ 36.38ms |
| TTL | 115 (모든 응답 동일) |
| 보냄 | 56개 |
| 받음 | 56개 |
| 손실 | 0개 (0%) |

평균은 개별 응답에 표시된 왕복 시간의 합계 2,037ms를 받은 패킷 56개로 나누어 계산했다.

> 측정 범위: 과제는 `ping -n 10 8.8.8.8`로 10회 전송하는 것이지만, 위 수치는 실제로 기록한 `ping 8.8.8.8` 14회 실행(실행당 4개, 총 56개 패킷)을 합산한 결과이다.

### 문제 2-3 · 이름으로 `ping` 보내기

- `google.com`의 IP 주소: 142.250.197.110 (2026-10-12 보고서 보완 시 같은 PC에서 `ping -4 google.com`으로 추가 측정).
- 이름만 입력했는데 IP 주소가 나온 이유는 무엇인가요?
  - 답: DNS가 `google.com`을 IP 주소로 변환해, 그 주소로 ping을 보낼 수 있기 때문이다.

### 문제 2-4 · 두 가지 실패를 구별하기

- 두 실패 문구와 멈춘 단계:

| 명령 | 실패 문구 | 멈춘 단계 |
|---|---|---|
| `ping abc.nowhere-not-exist` | Ping 요청에서 abc.nowhere-not-exist 호스트를 찾을 수 없습니다. 이름을 확인하고 다시 시도하십시오. | DNS 이름 해석 단계 |
| `ping 192.0.2.1` | 요청 시간이 만료되었습니다. | ICMP Echo Reply(응답)를 기다리는 단계 |

- 두 실패는 각각 어디에서 멈춘 것인가요?
  - 답: `abc.nowhere-not-exist`는 DNS에서 IP를 찾지 못해 ICMP 요청 전 단계에서 실패했다.
  - 답: `192.0.2.1`은 DNS 없이 요청했지만 제한 시간 안에 ICMP 응답을 받지 못했다. 문서용 예약 주소이며, 타임아웃만으로 차단·대상 부재 등 원인을 확정할 수 없다.

> `192.0.2.1`은 사설 IP가 아니라 문서·예시용 예약 대역인 TEST-NET-1(`192.0.2.0/24`)에 속한다. 출처: [IANA IPv4 특수 목적 주소 목록](https://www.iana.org/assignments/iana-ipv4-special-registry).

### ⭐ 도전 2-5 · `ping` 결과를 파이썬으로 판정하기

- 출력 결과:

```text
[정상] 8.8.8.8 34ms
[느림] 1.1.1.1 120ms
[실패] 192.0.2.1 응답 없음
```

위 출력은 `ping_check.py`에 미리 입력된 예시 데이터를 판정한 결과이며, 문제 2-2의 실측 평균과는 별개이다.

### 찾아본 것

- 2.1 표에서 찾아 쓴 TTL의 뜻과 라우터를 지날 때 바뀌는 방식: TTL(Time To Live)은 IP 패킷이 거칠 수 있는 남은 홉 수를 제한하는 값이다. 라우터를 하나 지날 때마다 1씩 감소하며, 0이 되면 패킷은 폐기된다. 이번 `ping` 결과의 TTL=115는 수신한 응답 패킷에 남아 있는 값이며, 왕복 시간이나 거쳐 온 라우터 수 자체를 뜻하지 않는다.

### 이 교시에 새로 안 것

- DNS 실패는 요청 전, 타임아웃은 요청 후 응답 대기 단계의 실패라는 것을 배웠다. 실측은 56개 전부 수신·손실 0%·평균 약 36.38ms였고 TTL 115는 거친 라우터 수가 아닌 남은 홉 값이다.

## 3교시 · IP 와 MAC

### 문제 3-1 · 결과 화면 읽기

- 예시 화면의 IPv4 주소 · MAC 주소 · 기본 게이트웨이:

### 문제 3-2 · 내 IP 주소 · 게이트웨이 · MAC 주소 찾기

- 찾은 장치 이름 · 내 IPv4 주소 · 기본 게이트웨이 · MAC 주소(물리적 주소):
  - 찾은 장치 이름: 이더넷 어댑터 이더넷 2
  - 내 IPv4 주소: 192.168.100.107
  - 게이트웨이: 192.168.1.1

  - 서브넷 마스크: 255.255.0.0

### 문제 3-3 · 게이트웨이까지 `ping`

- 게이트웨이까지 평균 · 2-2 의 `8.8.8.8` 평균:
  - 게이트웨이 `192.168.1.1`까지 평균: 0ms (Windows ping 통계 표시값). 최소 0ms, 최대 1ms이며, 개별 응답은 1ms 1개와 1ms 미만 3개였다. 보냄 4개, 받음 4개, 손실 0개(0%).
  - `8.8.8.8`까지 평균: 약 36.38ms (2-2에서 합산한 결과).

> 게이트웨이 값은 2026-10-12 보고서 보완 시 같은 PC(IP `192.168.100.107`, 기본 게이트웨이 `192.168.1.1`)에서 `ping -4 192.168.1.1`로 추가 측정했다. 평균 0ms는 정수로 표시된 통계값이므로 실제 왕복 시간이 전혀 없다는 뜻은 아니다. `8.8.8.8` 값은 앞서 기록한 측정 결과이다.
- 게이트웨이까지가 더 짧은 이유는 무엇인가요?
  - 답: 게이트웨이는 같은 내부망에 있지만 `8.8.8.8`은 외부 회선과 라우터를 거치기 때문이다. 실측은 게이트웨이 대부분 1ms 미만, `8.8.8.8` 평균 약 36.38ms였다.

### 문제 3-4 · ARP 캐시 보기 — `arp -a`

- 게이트웨이 줄의 MAC 주소 · 유형:
  - IP 주소: 192.168.1.1
  - MAC 주소: 00-10-f3-a3-fc-96
  - 유형: 동적
- 🔍 ARP 는 무엇을 알아내려고 쓰나요? 내 결과의 게이트웨이 줄을 예로 들어 설명합니다.
  - 답: ARP는 같은 링크에서 IP에 대응하는 MAC을 찾는다. 내 표의 게이트웨이 `192.168.1.1`은 `00-10-f3-a3-fc-96`에 대응한다.

### ⭐ 도전 3-5 · 주소 모양으로 IP 와 MAC 구별하기

- 출력 결과:

### 문제 4-2 · 지금의 연결 보기 — `netstat -n`

- 고른 줄의 외부 포트 → 서비스 이름:
  - 443 → HTTPS

  ```text
  활성 연결

    프로토콜  로컬 주소           외부 주소              상태
    TCP    192.168.100.107:50047  172.217.114.4:443      ESTABLISHED
  ```

외부 주소의 `:` 뒤 숫자 443을 실습 자료의 포트 표와 대조해 HTTPS로 분류했다. 내 쪽 포트 50047은 이 연결에 쓰인 임시 포트이며, 서비스 이름을 찾을 때는 상대 쪽 포트 443을 확인했다.

### 문제 4-3 · 그 연결은 어느 프로그램의 것인가

- PID → 프로그램 이름: 6512 → GoogleDriveFS.exe

내가 기록한 연결의 PID와 프로그램 이름이다. 보고서 검수 시에도 PID 6512의 프로세스 이름은 `GoogleDriveFS`로 확인됐다. 다만 4-2의 연결은 검수 시점에 목록에서 사라져, 해당 연결과 PID의 대응은 당시 내가 기록한 결과를 기준으로 남겼다.

### 문제 4-4 · 내 PC 의 LISTENING 포트 찾기

- 4.1 표에 있는 LISTENING 포트 → 서비스 이름:
  - 135 → RPC (Windows 원격 기능 호출)
  - 445 → SMB (Windows 파일·프린터 공유)
  - 3389 → RDP (Windows 원격 데스크톱)

2026-10-12 보고서 보완 시 같은 PC에서 `netstat -ano`로 확인한 LISTENING 줄 중 4.1 표에 있는 포트를 골랐다. 아래의 맨 끝 숫자는 PID이다.

```text
TCP    0.0.0.0:135    0.0.0.0:0    LISTENING    1788
TCP    0.0.0.0:445    0.0.0.0:0    LISTENING    4
TCP    0.0.0.0:3389   0.0.0.0:0    LISTENING    6856
```

- 🔍 LISTENING 과 ESTABLISHED 는 무엇이 다른가요? 4-2 와 4-4 에서 본 줄을 예로 들어 설명합니다.
  - 답: LISTENING은 연결 대기, ESTABLISHED는 TCP 연결 수립 상태다. 4-4의 `0.0.0.0:445`는 대기 중이고, 4-2의 `192.168.100.107:50047 → 172.217.114.4:443`은 연결된 상태다.

> `0.0.0.0`은 모든 로컬 IPv4 주소에서 연결을 기다린다는 뜻이다. LISTENING이라고 해서 외부 인터넷에서 실제로 접속할 수 있다는 뜻은 아니며, 접속 가능 여부는 방화벽과 네트워크 설정에도 영향을 받는다. ESTABLISHED도 연결이 맺어졌다는 뜻이며, 그 순간 계속 데이터를 주고받고 있다는 뜻은 아니다.

### 문제 4-5 · 증상으로 층 좁히기

- 증상 ① · ② · ③에서 의심되는 층:
  - ① IP로 ping은 되는데 이름으로는 호스트를 찾지 못함: 7층 응용 계층의 DNS 이름 해석 문제.
  - ② 기본 게이트웨이 ping 타임아웃: 내부망의 1~3층 문제를 우선 의심.
  - ③ ping은 되는데 특정 웹 사이트만 열리지 않음: 4층 이상의 포트나 웹 서비스 문제를 의심.

- 증상마다 그렇게 판단한 근거는 무엇인가요?
  - 답 ①: `8.8.8.8` ping은 성공했지만 `google.com`의 IP를 얻지 못했으므로, 7층 DNS 이름 해석을 먼저 확인한다.
  - 답 ②: 게이트웨이 타임아웃은 1~3층의 케이블·ARP·IP·마스크 설정 등을 우선 확인한다. ICMP 차단도 가능하므로 ARP 문제라고 확정할 수는 없다.
  - 답 ③: ping 성공은 ICMP 통신만 확인하므로 웹 접속 성공을 보장하지 않는다. 4층 TCP 포트·방화벽부터 TLS·웹 서비스까지 확인한다.

### 찾아본 것

- 4.1 표에서 찾아 쓴 3389의 위험과 445를 이용해 퍼진 랜섬웨어:
  - 3389는 Windows 원격 데스크톱(RDP)에 쓰이는 포트이다. 인터넷에서 접속할 수 있게 노출하면 비밀번호 추측이나 유출된 계정 정보, 취약점을 이용한 침입 시도의 대상이 될 수 있다. 필요 없는 원격 접속은 끄고, 필요한 경우에도 접속 범위와 인증을 관리해야 한다. 내 PC에서도 3389가 LISTENING으로 보였지만, 그것만으로 인터넷에 공개되어 있다고 판단할 수는 없다. 출처: [CISA 랜섬웨어 예방 가이드](https://www.cisa.gov/stopransomware/ransomware-guide).
  - 445는 Windows 파일·프린터 공유에 쓰이는 SMB의 TCP 포트이다. 대표적인 사례인 WannaCry(워너크라이, WannaCrypt)는 패치되지 않은 SMBv1의 취약점을 EternalBlue로 악용해 다른 컴퓨터로 퍼졌다. 445번 포트가 있다는 사실 자체가 감염을 뜻하는 것은 아니며, 취약한 SMB 서비스와 보안 업데이트 여부가 중요하다. 출처: [Microsoft의 WannaCrypt 분석](https://www.microsoft.com/en-us/security/blog/2017/05/12/wannacrypt-ransomware-worm-targets-out-of-date-systems/).

### 이 교시에 새로 안 것

- TCP·UDP 포트는 4층이며, 내 임시 포트와 상대 서비스 포트를 구분해야 한다. LISTENING은 연결 대기, ESTABLISHED는 연결 수립이고, PID로 프로그램을 찾을 수 있지만 ping 성공·대기 상태만으로 웹이나 외부 접속까지 보장되지는 않는다.

### 문제 5-2 · TCP 일까 UDP 일까

- ① ~ ⑤ 가 각각 TCP · UDP · ICMP 중 무엇인지:
  - 답: 실습 자료의 분류 기준으로 ① 사진 파일 보내기 → TCP, ② 실시간 방송 보기 → UDP, ③ `requests.post`로 LLM 부르기 → TCP, ④ DNS 조회 → UDP, ⑤ ping → ICMP이다.
- ① 사진 파일 보내기가 TCP 인 이유는 무엇인가요?
  - 답: TCP는 확인·재전송·순서 정리로 사진 파일의 빠짐 없는 전달을 지원한다. 이는 신뢰성이며 암호화를 뜻하지 않는다.

> 위 분류는 실습 자료의 예시이다. 실제 스트리밍이나 DNS의 사용 프로토콜은 서비스와 설정에 따라 달라질 수 있으므로, 모든 방송이 UDP이고 모든 DNS가 UDP라고 단정하지 않는다.

### 문제 5-3 · 세 번의 순서 맞히기

- 세 패킷의 순서와 방향:
  1. (나) `[SYN]`: 내 PC → 서버. 연결을 시작하자고 요청한다.
  2. (다) `[SYN, ACK]`: 서버 → 내 PC. 내 PC의 SYN을 확인하고, 서버 쪽 SYN도 함께 보낸다.
  3. (가) `[ACK]`: 내 PC → 서버. 서버의 SYN을 확인한다.

- 🔍 연결을 맺을 때는 세 번인데, 끝낼 때는 왜 네 번인가요?
  - 답: 연결은 서버가 SYN과 ACK를 함께 보내 세 단계다. 종료는 양쪽 송신을 따로 끝내 보통 FIN→ACK→FIN→ACK로 설명하지만, FIN·ACK가 합쳐지면 패킷 수는 달라질 수 있다.

참고: [RFC 9293 — TCP 연결과 종료](https://www.rfc-editor.org/rfc/rfc9293.html).

### 문제 5-4 · 같은 서버로 간 두 연결은 무엇이 다른가

- 두 연결에서 같은 것 · 다른 것:
  - 실습 자료의 예시 기준으로 같은 것은 내 IP `192.168.0.15`, 서버 IP `142.250.196.110`, 서버 포트 `443`, 프로토콜 TCP, 상태 ESTABLISHED이다.
  - 다른 것은 내 PC의 임시 포트로, 첫 번째 연결은 `51234`, 두 번째 연결은 `51240`이다. 이 주소와 포트는 실습 자료의 예시이며 내 PC의 실측값은 아니다.
- 같은 서버로 간 두 연결을 무엇으로 구별하나요?
  - 답: TCP 연결은 양쪽 IP·포트 네 값으로 구별한다. 이 예시는 다른 값이 같고 내 임시 포트만 달라 두 연결을 구별한다.

### 이 교시에 새로 안 것

- 리스트의 플래그는 문자열과 `==` 비교하지 말고 `in`으로 확인한다. TCP는 재전송·순서 정리와 양쪽 IP·포트로 신뢰성·연결 구분을 제공하며, 연결은 세 단계·종료는 보통 네 단계지만 암호화는 별개이고 ping은 ICMP다.

#### 문제 6-3 · 패킷 하나를 층별로 펼치기

- 선택한 패킷의 상세 값:

| 계층 | 항목 | 기록한 값 |
|---|---|---|
| 2층 Ethernet | Source MAC | 00:10:f3:a3:fc:96 |
| 3층 IPv4 | Source IP | 104.20.23.243 |
| 3층 IPv4 | Destination IP | 192.168.100.107 |
| 3층 IPv4 | Time to Live | 52 |
| 4층 TCP | Source Port | 443 |
| 4층 TCP | Destination Port | 52945 |
| 4층 TCP | Flags | ACK |

추가로 Info에는 `Seq=1 Ack=67 Win=16 Len=0`이 표시됐다. 이 값들은 플래그와 별도의 정보이며, `Len=0`은 이 TCP 세그먼트에 데이터가 없다는 뜻이다. 패킷 전체 길이가 0이라는 뜻은 아니다.

- 이 패킷은 내 PC 가 보낸 것인가요, 받은 것인가요? 어떻게 알았나요?
  - 답: 목적지가 내 IP `192.168.100.107`이고 443→내 임시 포트 52945이므로 받은 패킷이다. 웹 본문이 아닌 ACK 확인 패킷이다.

Source MAC은 오전에 확인한 게이트웨이의 MAC `00-10-f3-a3-fc-96`과 같은 값이다. 외부 서버에서 온 IP 패킷을 같은 링크의 게이트웨이가 내 PC로 전달했으므로, Source IP는 외부 서버인데 Ethernet의 Source MAC은 게이트웨이로 보인다. 이를 통해 IP는 통신 상대를, MAC은 현재 링크의 전달 장비를 가리킨다는 차이를 확인했다.

#### 문제 6-4 · 필터 결과와 뜻 비교하기

- 같은 캡처에서 기록한 전체 Packets와 필터별 Displayed:

| 표시 필터 | 개수 | 의미 |
|---|---|---|
| 전체 Packets | 589 | 캡처한 전체 패킷 수 |
| `dns` | 32 | DNS로 해석된 패킷 수 |
| `udp` | 468 | UDP를 포함한 패킷 수 |
| `tcp.port == 443` | 67 | 출발지 또는 목적지 TCP 포트가 443인 패킷 수 |

- 필터를 걸어도 `Packets` 는 그대로인데 `Displayed` 만 바뀌는 이유는 무엇인가요?
  - 답: 표시 필터는 원본 589개를 보존하고 일치하는 패킷만 Displayed에 보여 준다. 필터를 지우면 전체를 다시 볼 수 있다.

필터를 적용하면서 직접 확인한 내용:

- `udp`를 적용했는데 Protocol 열에 DNS도 보였다. 이번에 본 DNS 메시지가 UDP 안에 담겨 전송됐기 때문이다.
- `tcp.port == 443`을 적용했는데 TCP와 TLSv1.2가 함께 보였다. TLS 데이터도 TCP 안에 담겨 전송되고, 그 TCP의 출발지나 목적지 포트가 443이면 조건에 맞기 때문이다.
- Protocol 열의 이름 하나가 패킷 안의 모든 계층을 뜻하는 것은 아니다. 표시 필터는 해당 프로토콜이나 필드가 패킷에 있는지 확인하므로, 열에 표시된 이름과 필터 이름이 달라도 정상이다.
- 같은 패킷이 여러 필터에 포함될 수 있고 어느 필터에도 포함되지 않는 패킷도 있으므로, 필터별 개수를 합쳐 전체 589개와 맞출 필요는 없다. DNS가 전부 UDP였는지는 이 숫자만으로 확정할 수 없다.

참고: [Wireshark 공식 문서 — 표시 필터](https://www.wireshark.org/docs/wsug_html_chunked/ChWorkDisplayFilterSection), [필터 표현식](https://www.wireshark.org/docs/wsug_html_chunked/ChWorkBuildDisplayFilterSection).

### 이 교시에 새로 안 것

- 패킷 상세 창에서 MAC·TTL을 확인하고, 목적지 IP와 포트로 방향을 판단하되 서버발 ACK를 웹 본문으로 혼동하지 않아야 한다. 실측 589개에서 표시 필터는 원본을 보존했으며, 외부 서버 IP와 게이트웨이 MAC이 한 패킷에 함께 보일 수 있었다.

- 깃허브 `network_zt` 폴더에 보고서가 보이나요: 예 — 업로드 완료로 기록함(사용자의 완료 처리 기준).

### 이 교시에 새로 안 것

- TCP Stream에서 38~40번의 SYN→SYN·ACK→ACK와 `GET / HTTP/1.1`, `200 OK`를 확인했다. 종료 FIN은 FIN·ACK 형태로 양쪽 총 2개였고, HTTPS는 HTTP 내용을 보호하지만 IP·포트까지 숨기지는 않는다.

## 최종 분석 — 7교시에 완성합니다

> 7교시에서 잡은 HTTP 연결 `tcp.stream eq 5`를 처음부터 끝까지 정리한다. 6-3에서 분석한 HTTPS 패킷은 다른 연결이므로 따로 구분했다.

### 1. 연결이 열리는 순간 — 3-way handshake

- 세 줄의 Source → Destination 과 Info:
  - 38번: `192.168.100.107 → 172.66.147.243`, `56428 → 80 [SYN]`.
  - 39번: `172.66.147.243 → 192.168.100.107`, `80 → 56428 [SYN, ACK]`.
  - 40번: `192.168.100.107 → 172.66.147.243`, `56428 → 80 [ACK]`.
- 세 줄이 오간 뒤 두 컴퓨터는 어떤 상태가 되나요?
  - 답: 양쪽이 SYN을 주고받고 확인해 TCP 연결이 맺어진 ESTABLISHED 상태가 된다. 그 뒤 내 PC가 41번 패킷에서 HTTP 요청을 보냈다.

### 2. 패킷 하나를 열어 본 값 — 6-3

- 출발지 · 목적지 IP (3층) · TTL · 출발지 · 목적지 포트 (4층):
  - 7교시 HTTP 요청(41번): 출발지 IP `192.168.100.107`, 목적지 IP `172.66.147.243`, TTL `128`(사용자가 패킷 상세에서 확인), 출발지 포트 `56428`, 목적지 포트 `80`.
  - 6-3의 별도 HTTPS 수신 패킷: 출발지 IP `104.20.23.243`, 목적지 IP `192.168.100.107`, TTL `52`, 출발지 포트 `443`, 목적지 포트 `52945`, Flags `ACK`.
- 목적지 포트를 보고 어떤 서비스로 가는 패킷인지 알 수 있나요? 4.1 표를 근거로 설명합니다.
  - 답: 7교시는 목적지 80과 `GET / HTTP/1.1`로 HTTP 요청임을 확인했다. 6-3의 목적지 52945는 PC 임시 포트로, 서버 443에서 돌아오는 방향이며 포트만으로 내용은 확정하지 않는다.

### 3. HTTP 요청 — 7-2

- 요청 줄에서 그대로 보인 내용:
  - 41번: `GET / HTTP/1.1`. 실행한 요청에 검색어는 포함되지 않았다.
- 이것이 보안에서 문제가 되는 이유는 무엇인가요?
  - 답: HTTP는 암호화하지 않아 경로에서 패킷을 보는 사람이 요청 내용을 읽을 수 있다. 실측은 `/`만 보였지만 민감 정보도 노출될 수 있어 HTTPS로 보호해야 한다.

### 4. 오늘 하루 정리

- 오늘 배운 것 가운데 가장 중요하다고 생각하는 것과 그 이유:
  - 답: DNS 실패·ping 타임아웃·웹 접속 실패를 구분하고, 어느 단계까지 동작했는지 확인하는 것이 중요하다. 패킷의 주소·포트·TCP 상태를 근거로 관찰과 추정을 구분해야 한다.
