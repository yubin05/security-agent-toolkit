# 2026-10-12 오전 학습 노트 · OSI 계층과 네트워크 첫 관찰

범위: 2~4교시. 기존 보고서와 수업 자료를 대조해 정리했으며, 이번 정리에서 새 측정은 하지 않았다. 오후 5~6교시 기록은 제출 보고서에 보존했고, 7교시와 최종 분석은 작성하지 않았다.

## 1. 통신을 계층으로 나누어 보는 이유

인터넷이 안 된다는 증상 하나에도 케이블, 주소 설정, 이름 해석, 포트, 서비스 등 여러 원인이 있다. OSI 계층은 어디부터 확인할지 나누어 생각하는 기준이다.

| 계층 | 핵심 역할 | 오전에 연결한 개념·명령 |
|---|---|---|
| 7 응용 | 웹·DNS 같은 서비스 | 이름 해석, 웹 응답 |
| 6 표현 | 데이터 표현·암호화·압축 | HTTPS의 암호화 이해 |
| 5 세션 | 대화의 시작·유지·종료 관리 | 통신 흐름 이해 |
| 4 전송 | TCP·UDP, 포트 | `netstat`, 서비스 포트 |
| 3 네트워크 | IP와 라우팅 | `ping`, TTL, 게이트웨이 |
| 2 데이터링크 | 같은 링크의 프레임 전달 | MAC, ARP, 스위치 |
| 1 물리 | 전기·빛·전파로 신호 전달 | 랜선, Wi-Fi |

TCP/IP 4계층에서는 OSI 5~7층을 응용, 4층을 전송, 3층을 인터넷, 1~2층을 링크로 묶는다. 실제 프로토콜의 기능이 OSI 한 층에 정확히 대응하는 것은 아니다.

## 2. ping · 성공과 실패가 말해 주는 범위

ping은 ICMP Echo 요청과 응답으로 도달 여부와 왕복 시간을 확인한다. `8.8.8.8`이 DNS 서버라고 해서 ping으로 DNS 질의까지 검사한 것은 아니다.

| 기존 보고서의 실측 항목 | 기록값 | 해석·측정 범위 |
|---|---|---|
| `8.8.8.8` 응답 | 보냄·받음 각 56개, 손실 0% | 기본 ping 14회 실행, 회당 4개 합산 |
| 평균 왕복 시간 | 36.375ms ≈ 36.38ms | 표시된 응답 시간 합계 2,037ms ÷ 56 |
| 응답 TTL | 115 | 돌아온 응답에 남은 값 |
| `google.com` IPv4 | 142.250.197.110 | 기존 보완 기록의 `ping -4 google.com` 결과 |
| 게이트웨이 ping | 평균 0ms, 최소 0ms, 최대 1ms, 손실 0% | 기존 추가 측정 4개 응답; 정수 통계 표시값 |

**예시와 구분:** 문제 2-1의 4개 전송·3개 수신·25% 손실·47ms와 도전 코드의 34ms·120ms는 수업 예시다. 위 실측값과 섞지 않는다. 과제의 10회 전송 결과를 새로 만든 것은 아니다.

### 헷갈렸던 점 → 이해한 내용

- 호스트를 찾지 못함도 Echo 전송 실패라고 생각했다 → `abc.nowhere-not-exist`는 목적지 IP를 얻지 못한 DNS 단계 실패다.
- `192.0.2.1`은 사설 IP라 실패한다고 생각했다 → 문서용 TEST-NET-1 주소다. 타임아웃은 응답을 제한 시간 안에 받지 못했다는 뜻이며, 원인까지 확정하지 못한다.
- TTL=115를 지나온 라우터 수로 읽기 쉽다 → 응답의 남은 값이다. PDF의 128−13=115는 시작값을 가정한 예시이며 실제 홉 수·OS를 확정하지 못한다.
- 게이트웨이 평균 0ms → 실제 시간이 0이라는 뜻이 아니다. 정수 통계이며, 개별 응답은 1ms 1개와 1ms 미만 3개였다.

TTL이 소진되면 패킷은 폐기되고 ICMP Time Exceeded가 올 수 있다. 원래 패킷이 되돌아오는 것은 아니다. 재전송은 TCP 같은 상위 프로토콜이나 프로그램이 결정한다.

## 3. IP·MAC·ARP · 목적지와 다음 전달 장비 구분

| 내 환경의 기존 기록 | 값 |
|---|---|
| 인터페이스 | 이더넷 어댑터 이더넷 2 |
| IPv4 / 마스크 | 192.168.100.107 / 255.255.0.0 |
| 기본 게이트웨이 | 192.168.1.1 |
| 내 MAC | D8-BB-C1-40-36-81 |
| ARP의 게이트웨이 MAC | 00-10-f3-a3-fc-96, 동적 |

마스크가 `/16`이므로 내 IP와 게이트웨이는 `192.168.0.0/16`에 함께 속한다. IP의 앞 세 숫자만 보고 다른 망이라고 판단하면 안 된다.

ARP는 같은 링크에서 IP에 대응하는 MAC을 찾는다. 캐시에 정보가 없으면 요청을 브로드캐스트하고, 응답을 받아 대응 정보를 저장한다. 외부 서버로 보낼 때는 서버의 MAC이 아니라 같은 링크의 게이트웨이 MAC을 사용한다. `ff-ff-ff-ff-ff-ff`는 이더넷 브로드캐스트 주소다.

**생각이 바뀐 과정:** 처음에는 ARP의 ‘동적’이 DHCP로 IP를 배정받았다는 뜻인 줄 알았다. 실제로는 IP–MAC 대응을 자동으로 알아내 저장한 ARP 항목이다. 기록된 `192.168.100.xxx` 동적 항목 67개도 출석 인원이나 학생 PC 수로 확정할 수 없다.

주소 크기: 1바이트는 8비트, 16진수 두 자리는 1바이트다. 일반적인 MAC은 6바이트(48비트), IPv4는 4바이트(32비트)다.

## 4. 포트·연결 상태 · 어느 프로그램의 통신인가

포트는 TCP·UDP의 4층 정보다. IP가 통신 상대를 가리키고 포트가 서비스·연결을 구분한다. 익숙한 용도는 SSH 22, DNS 53, HTTP 80, HTTPS 443이다. 포트 번호만으로 실제 통신 내용을 확정하지 않는다.

기록한 연결은 `192.168.100.107:50047 → 172.217.114.4:443`, TCP ESTABLISHED였다. 내 임시 포트 50047과 상대 서비스 포트 443을 구분한다. 당시 PID–프로그램 기록은 `6512 → GoogleDriveFS.exe`다. 이전 검수에서 프로세스 이름은 확인했지만 연결은 이미 사라졌으므로, 대응 관계는 당시 기록을 근거로 남긴다.

기존 추가 측정의 LISTENING 포트는 135(RPC), 445(SMB), 3389(RDP)였다. LISTENING은 요청 대기, ESTABLISHED는 연결 성립 상태다. 연결 성립이 계속 데이터 전송 중이라는 뜻은 아니며, 모든 로컬 IPv4 주소에서 대기하는 `0.0.0.0`도 인터넷 공개를 보장하지 않는다.

### 헷갈렸던 점 → 이해한 내용

- `.get()`이 예외를 처리한다고 생각했다 → 없는 키에 지정한 기본값을 반환한다. 실습 출력 `HTTPS`, `모름`은 사전 조회 예시다.
- 포트를 7층으로 생각했다 → TCP·UDP 포트는 4층이며, 웹·DNS 서비스의 역할과 구분한다.
- 게이트웨이 타임아웃을 ARP 문제로 단정했다 → 1~3층을 우선 확인하되 ICMP 응답 정책도 고려한다.
- ping이 성공하면 웹도 된다고 생각하기 쉽다 → DNS, TCP 포트, 방화벽, TLS, 웹 서버를 따로 확인해야 한다.

보안 연결: RDP는 접속 범위·인증을 관리해야 하고, SMB는 업데이트 여부가 중요하다. WannaCry는 취약한 SMBv1을 악용해 확산한 사례이며 445번이 보인다는 사실 자체가 감염 증거는 아니다.

## 5. 오전 내용을 한 흐름으로 연결하기

외부 HTTPS 요청은 서버 IP와 서비스 포트 443을 목적지로 사용한다. 첫 링크에서는 ARP로 알아낸 게이트웨이 MAC으로 전달한다. 스위치는 MAC, 라우터는 IP·경로를 보고 전달한다. 공유기는 라우터·스위치·Wi-Fi 기능을 함께 제공할 수 있다.

데이터에 TCP → IP → 링크 계층 정보를 붙이는 것이 캡슐화이고, 수신 측이 이를 해석해 프로그램으로 전달하는 것이 역캡슐화다. 계층별로 TCP 세그먼트, IP 패킷, 이더넷 프레임이라고 부른다. MAC은 링크마다 달라지며, 일반 라우팅과 달리 NAT/NAPT에서는 IP·포트도 변환될 수 있다.

## 오전 수업 PDF 복습 정리

> 실습 답을 작성한 뒤 수업 PDF와 비교해 보완한 내용이다. 아래 개념 설명은 추가로 정리한 것이며, 새로 측정한 결과는 아니다. 참고 자료: `docs/1012-am-osi-layers.pdf`.

### 1. 데이터의 크기와 주소 표기 (PDF 6쪽)

- 비트(bit)는 0 또는 1을 나타내는 가장 작은 단위이고, 1바이트(byte)는 8비트이다.
- 16진수는 0~9와 A~F를 사용한다. 두 자리의 16진수로 1바이트를 표시할 수 있다.
- 일반적인 MAC 주소는 6바이트(48비트), IPv4 주소는 4바이트(32비트)이다. 내 MAC `D8-BB-C1-40-36-81`은 16진수 여섯 묶음이고, 내 IPv4 `192.168.100.107`은 점으로 구분한 네 묶음이다.

### 2. OSI 계층과 장비의 역할 (PDF 8·25·28쪽)

| 계층 | 역할 | 이번 실습과 연결 |
|---|---|---|
| 7 응용 | 웹·DNS 같은 서비스 | 도메인 이름 해석, 웹 서비스 |
| 6 표현 | 데이터 표현·암호화·압축 | 암호화된 통신을 이해할 때 참고 |
| 5 세션 | 대화의 시작·유지·종료 관리 | 연결과 대화의 흐름을 이해할 때 참고 |
| 4 전송 | TCP·UDP와 포트 | netstat의 포트·TCP 연결 상태 |
| 3 네트워크 | IP 주소와 라우팅 | ipconfig, ping, 라우터 |
| 2 데이터링크 | 같은 링크에서 프레임 전달 | MAC 주소, ARP, 스위치 |
| 1 물리 | 전기·빛·전파로 신호 전달 | 랜선, Wi-Fi |

스위치는 같은 링크에서 MAC 주소를 보고 프레임을 전달하고, 라우터는 IP 주소와 경로 정보를 이용해 다른 망으로 패킷을 전달한다. 기본 게이트웨이는 외부 망으로 보낼 때 사용하는 다음 라우터이다. 공유기는 보통 라우터 기능에 스위치·Wi-Fi 같은 기능을 함께 제공한다.

실무의 TCP/IP 4계층 모델은 OSI의 5~7층을 응용, 4층을 전송, 3층을 인터넷, 1~2층을 링크 계층으로 묶어 이해한다. 실제 프로토콜의 기능이 OSI의 한 층에만 정확히 들어맞는 것은 아니다.

### 3. ARP는 IP를 MAC으로 연결한다 (PDF 33~35쪽)

내 PC가 같은 링크의 게이트웨이 `192.168.1.1`로 보내려면 그 장비의 MAC 주소가 필요하다.

1. 캐시에 대응 정보가 없으면, 같은 링크에 “192.168.1.1의 MAC 주소가 무엇인가?”라는 ARP 요청을 브로드캐스트한다.
2. 일반적인 경우 해당 IP를 가진 장비가 자신의 MAC 주소를 응답한다.
3. 내 PC가 이 대응 정보를 캐시에 저장해 다음 전송에 사용한다.

내 결과의 대응은 `192.168.1.1 → 00-10-f3-a3-fc-96`이었다. `ff-ff-ff-ff-ff-ff`는 특정 PC의 MAC이 아니라 이더넷 브로드캐스트 주소이다. 외부 서버로 보내는 경우에는 외부 서버의 MAC을 ARP로 찾는 것이 아니라, 같은 링크에 있는 다음 장비인 게이트웨이의 MAC을 찾는다.

### 4. 웹 요청에서 IP·MAC·포트를 함께 사용한다 (PDF 47쪽)

예를 들어 외부 HTTPS 서버로 요청을 보내면, 목적지 IP는 최종 서버를 가리키고 목적지 포트 443은 그 서버의 HTTPS 서비스를 가리킨다. 내 PC에서 처음 나가는 이더넷 프레임의 목적지 MAC은 게이트웨이의 MAC이다.

라우터를 거쳐 새로운 링크로 나갈 때는 그 링크에 맞는 프레임을 새로 만들므로, MAC 주소는 링크별로 달라진다. IP와 포트는 일반적인 라우팅만으로는 바뀌지 않지만, NAT/NAPT를 거치면 IP 주소나 TCP·UDP 포트가 변환될 수 있다. 따라서 “인터넷을 지나는 동안 모든 IP와 포트가 항상 그대로다”라고 단정하면 안 된다. 참고: [RFC 3022 — NAT와 주소·포트 변환](https://www.rfc-editor.org/rfc/rfc3022.html).

### 5. 캡슐화와 역캡슐화 (PDF 48쪽)

보내는 쪽은 웹 요청 데이터에 TCP 헤더(포트 등), IP 헤더(IP·TTL 등), 링크 계층 정보(MAC 등)를 차례로 붙여 전송한다. 이렇게 각 계층의 정보를 덧붙이는 과정을 **캡슐화**라고 한다. 받는 쪽은 계층별 정보를 해석하고 벗겨 알맞은 프로그램으로 전달하는 **역캡슐화**를 수행한다.

같은 데이터를 계층에 따라 TCP 세그먼트, IP 패킷, 이더넷 프레임으로 부른다. 오후 Wireshark에서 한 통신의 Ethernet·IP·TCP 부분을 펼쳐 보면 오전에 배운 주소와 포트를 함께 확인할 수 있다.

### 6. TTL이 0이 된 뒤와 응답 TTL의 의미 (PDF 12~15쪽)

TTL이 0이 된 패킷은 폐기된다. 라우터가 보낸 쪽에 ICMP Time Exceeded(시간 초과) 메시지를 보낼 수 있지만, 버린 원래 패킷을 되돌려 주는 것은 아니다. 데이터가 필요한 경우 재전송 여부는 상위 프로토콜이나 프로그램이 결정한다. TCP는 응답 확인이 없으면 조건에 따라 재전송하고, UDP는 프로토콜 자체에서 재전송을 보장하지 않는다. 참고: [RFC 792 — ICMP Time Exceeded](https://www.rfc-editor.org/rfc/rfc792/).

ping 출력의 TTL은 **응답 패킷이 돌아오는 경로에서 감소한 뒤 남은 값**이다. PDF의 “128에서 출발해 라우터 13대를 지나 115가 된다”는 설명은 시작값을 128로 가정한 예시이다. 내 결과의 TTL=115만으로 서버의 운영체제나 정확한 라우터 수를 확정할 수는 없다. 같은 링크에서 스위치를 통과하는 것만으로 IP TTL이 감소하는 것도 아니다.

### 7. 관제에서 판단 범위를 구분하기 (PDF 11·19·32·46쪽)

- `ping 8.8.8.8` 성공은 그 IP와 ICMP 요청·응답이 오갔다는 뜻이다. 대상이 DNS 서버여도 이 명령으로 DNS 질의나 웹 접속을 시험한 것은 아니다.
- ping 실패만으로 서버가 꺼졌다고 단정하지 않는다. ICMP 차단이나 응답 제한도 원인이 될 수 있다.
- 게이트웨이와 외부 IP의 결과를 비교하면 문제 범위를 좁히는 데 도움이 되지만, 각각의 ICMP 응답 정책까지 고려해야 한다.
- “포트 443 → HTTPS”는 일반적인 포트 용도에 따른 분류이다. 포트 번호만으로 실제 프로그램이나 통신 내용을 확정하지 않고, PID·프로세스와 필요하면 패킷 내용까지 확인한다.

### 8. 제출 전 남은 점검

- 2-2의 과제 명령은 `ping -n 10 8.8.8.8`이다. 현재 56개 합산 기록은 계산상 맞고 측정 범위도 명시했지만, 과제 형식을 엄격히 따르려면 10개 전송 결과를 별도로 추가해야 한다.
- 보고서 제목의 이름은 아직 “이름”으로 남아 있으므로 제출 전에 실제 작성자 이름을 적는다.
- 현재까지의 문서화는 오전 2~4교시 범위이다. 오후 5~7교시와 최종 분석은 해당 실습 뒤 실제 관찰값을 채운다.
